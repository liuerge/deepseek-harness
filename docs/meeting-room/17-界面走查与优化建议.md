# 界面走查与优化建议

## 目的与范围

本轮在 WSL 预览实例（base + web-app + meeting-room-bundle）上，用五子棋复杂场景的真实成果数据走查「需求提出 → 团队模式 → 计划确认 → 派工执行 → 独立验收 → 交接与成果」整条用户路径，逐屏截图留档；走查后先判断各环节是否合理，再给出分级优化建议。留档图片与本文件同目录（`ui-review-20261119/`），本轮对「团队模式」说明的修复见文末。

## 合理性梳理

**成立、应保留的部分**

- 信息架构与用户心智一致：员工与团队 → 项目计划与确认 → 执行与验收 → 交接与成果，自上而下一路回答「谁来做、做什么算完成、做到哪了、交了什么」。
- 每块开头有一句规则说明（例如「每名员工独立选择模型连接与模型；保存配置不会启动工作或改变已确认计划」「选择团队只设定规划默认值……」），解释了权限边界，减少误操作。
- 关键事实齐全：版本号、确认状态、关联文档、逐项标准、返工上限、Team 任务状态、交接记录都能在一页找到，无需跳转。
- 「逐项验收约定」「验收报告」「背景材料」「交接记录」默认折叠，长文不压首屏；本轮留档只覆盖浅色设置、深色设置与深色工作台首屏，这些区域的层次和对比度成立。
- 前置条件不足时给出原因（未选工作区时团队模式菜单项禁用并说明），符合错误可解释的要求。
- 模式菜单由四个互斥预设（标准/PTC/极简/创造）加一个可叠加的「团队模式」入口组成：团队模式是独立开关，可与标准或其他预设同时生效，不设为互斥预设；这条非互斥语义已验证（证据见 `02-产品设计与交互.md:21`、`06-实施记录.md:480`、`:530`），实现是 `conversation.hero.agentPreset.options` slot 注入带 `separatorBefore` 的 `MenuItemButton`。

**判定为不合理的部分**

1. 状态不可扫读：「已确认」「已完成」「任务已产出」「Agent 检查通过」「通过」均为纯文本或普通加粗，没有状态色或图标；同一页要逐字读完才能定位失败或待处理项。
2. 同一事实重复：目标句与两条任务的指令原文在「项目计划与确认」和「执行记录」各出现一次，页面长度约翻倍，用户还需跨区块对照是否是同一版本。
3. 技术细节直出：计划文档显示为绝对路径，验收证据与「已核对的产物版本」显示完整路径与 64 位哈希；不可点击、不可复制，只能肉眼比对。
4. 用户可见文案技术化：「提出需求/修改计划/委托团队」预填的提示词直接出现 `employee_list`、`project_plan_save`、`artifactPaths` 等工具与字段名，超出普通用户的理解范围，也与「简单描述」的预期不符。
5. 弹窗动作区拥挤：团队弹窗宽 380px，「配置员工与团队 / 清除团队选择 / 刷新进度」三个文字按钮折成两行且最后一项孤立；真正的主操作是列表内的「使用 团队」，动作层级不清。
6. 文案重复与折行：「模型连接 / 厂商」在同一连接下显示「opencode-go · opencode-go」（名称与 id 重复）；成员行模型 id 在连字符处折成「deepseek-v4.1- / flash」。
7. 大位移：编辑员工为内联展开，把整页推下约 600px，收起后需要重新定位。
8. 超宽屏行宽过长：1880px 视口下正文列约 1500px，英文长句单行超过 140 字符，阅读成本高。
9. 组合标签截断：输入框上方的「团队模式 · 五子棋交付团队」在按钮宽度内截断为「团队模式 · 五子棋交付…」，没有悬停提示补全。

## 优化建议

**P0：一致性与正确感**

1. 状态 chip：为计划确认、执行状态、任务状态、验收结论提供统一样式（状态点 + 文案，复用 `--dsw-alias-state-*` 语义 token，不铺色块），不再用纯文本表达「通过/不通过/无法验证」。`08-UI出图需求.md:11` 的 HEX 是出图稿验收值、不约束工作台，`docs/web-styling.md:18` 才禁止在特性组件中写字面色值。状态枚举需覆盖受阻/返工中/待确认/未开始等失败与待处理态，并补失败态截图才能验收（当前走查数据全是成功态）。
2. 执行区去重：执行记录只显示「依据计划版本 N」的摘要（目标引用、状态、指向计划块），任务指令与验收原文仅保留在计划块，跨块导航用锚点。
3. 弹窗动作重排：主操作保持列表内「使用团队」；底部只留「清除团队选择」与刷新图标按钮（带 aria-label），「配置员工与团队」移到弹窗内容区（Modal 标题右侧无该槽位；工作台右上已有「配置员工/配置团队」直达入口），保证 380px 内不折行。

**P1：可读性与可操作性**

4. 内容列限宽：主内容列限制在约 1100px 并居中，长文本行宽不超过约 90 字符。
5. 路径与哈希组件化：用文件 chip 呈现（basename + 悬停全量路径 + 文件操作；`ui-primitives` 无通用文件图标，故不带图标）；复用 `ui-open-in-app` 的 `contextMenus` file target，同包 `SessionArtifacts.tsx` 已实现 basename + 全量路径 + 既有文件操作的范式。哈希截断显示前 8 位，完整值放悬停或复制。`ctx.fileActions` 只有 save/copyImage/canSaveAs，不是打开/复制/显示位置的来源。
6. 用户提示词去技术化：把 `employee_list`、`project_plan_save`、`artifactPaths` 等替换为目标句式（例如「请基于我的需求准备项目计划草稿，包含目标、任务与验收方式；保存后请在项目工作台确认版本」），具体工具参数由主助手内部展开。
7. 模型显示去重：下拉项 name 与 id 相同时只显示一次；成员行模型 id 保持弹窗 380px、不折行加省略号（`ui-primitives/Modal.module.css:40` 的 380px 是全局值，加宽回归面大）。

**P2：打磨**

8. 员工编辑改为弹窗或抽屉（或行内展开时保持滚动锚点），避免整页位移。
9. 验收报告改为逐项行：每条 AC 一行（状态 chip + 一句结论），证据与原文折叠；「已核对的产物版本」改用文件 chip。
10. 组合按钮补全名：为「团队模式 · 团队名」加 title/aria-label，或拆成两段各自可点击。
