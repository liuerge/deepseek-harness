# 技术方案与阶段计划

## 架构总览

```
DSH 桌面/Web（Electron + Web UI）
├─ 会议插件（本产品）
│  ├─ host 服务（Cordis 插件）
│  │  ├─ 领域服务：项目/团队/角色 Agent/会议/任务/验收/预算/评价
│  │  ├─ 编排服务：会议状态机、任务调度、主助手编排
│  │  └─ 存储：插件自有数据目录（SQLite/JSON）
│  └─ client UI（插件页面）
│     ├─ 主助手（对话 + 运行时间线）
│     ├─ 会议列表/详情
│     ├─ 任务/验收
│     ├─ Agent 库
│     └─ 技能/MCP
├─ DSH 能力（复用）
│  ├─ 会话/Agent 循环、工具执行、沙箱/审批
│  ├─ 模型适配器、MCP、技能扫描
│  └─ 设置/凭据/插件管理与市场
└─ 模型来源：Magpie / 原生 Codex / Claude / OpenCode Go / 直接 API
```

## 关键设计

- **插件而非 fork 核心**：会议业务作为 DSH 插件 + 客户端 UI 包，尽量不修改 DSH 核心；上游可更新。
- **Agent 运行时复用 DSH 会话**：每个角色 Agent 一轮 = 一个 DSH 会话/线程；编排服务负责发起、收集、落库、推进状态机。
- **治理在服务端**：独立首轮、争议台账、终审/发布门槛由代码保证，模型不能绕过。
- **存储独立**：插件数据与 DSH 会话日志分开；数据目录可备份/导出。
- **审批统一**：工具/命令/MCP 调用走 DSH 审批或插件审批适配层，可按任务显式授权。

## 数据模型（初稿）

- project: id, name, directory, background, management, budget
- agent: id, name, kind(role/capability), shell/model, prompt, permissions, roles, skills, disabled
- team: id, project, type, name, members, leader
- meeting: id, project, title, requirement, materials, status, stage, rounds, members, decisions, plan_versions
- meeting_message: id, meeting, agent, role, content, round, state, timing, usage
- task: id, project/meeting, title, requirement, acceptance, members, status, calls_used/max, artifacts, checks, error
- artifact: id, task, relative, sha256, bytes, format, accepted
- budget_request: id, project, calls, reason, status
- rating: id, task, agent/team, scores, evidence, final
- skill: id, name, description, requires, instructions
- mcp_server: id, name, transport, command/url, tools(allowlist), enabled

## 阶段计划

### Stage 0：Spike（1～2 天）

先验证 DSH 已有的智能体团队能力，再验证插件页面：
1. 开启 DSH Team 模式：确认 Subagent 树、共享任务板、任务状态与负责人可用。
2. 插件加两页：主助手会话页、会议列表/详情（假数据），复用 Conversation 渲染扩展点。
3. 用 2 个角色子代理各独立回答一轮，写回会议详情/共享任务。
4. 调用一个 MCP 工具（文件类），展示结果与审批。
5. 打 Electron 安装包，插件随应用启动，数据重启不丢。

**通过**：Team 模式可用、两页可加、两子代理可独立跑、MCP 可调、桌面包可装。否则回退"现有会议室 + MCP/技能"混合路线。

### Stage 1：会议插件 v1（约 1～2 周）
- 项目/角色/团队/会议/轮次/意见/决策的存储与服务
- 会议状态机：独立首轮 → 讨论 → 综合裁决 → 独立终审 → 发布
- 主助手拆解并创建会议、收集结果
- 验收：一场完整会议可创建、推进、暂停/恢复、终审、发布；重启不丢；离线测试覆盖。

### Stage 2：任务与验收（约 1～2 周）
- 任务看板、执行（DSH 工具）、审核/验收/返工、产物登记、预算
- 运行时间线与 L2 审批；失败/超时原因可见
- 验收：合成任务从创建到验收跑通；文件指纹与检查证据；预算不超。

### Stage 3：技能、MCP、角色库（约 1～2 周）
- SKILL.md 导入/分配/路由；MCP 服务器管理（含 Magpie hub）；能力 Agent（文件/搜索/浏览器）
- 预置角色 Agent 模板与默认权限
- 验收：导入 3 个技能、分配生效；MCP list/call；权限拒绝可见。

### Stage 4：迁移与交付（约 1 周）
- 现有会议室 SQLite 导出 → 新 schema 导入（项目/Agent/团队/讨论/任务）
- 旧应用保留为回退；桌面安装包、设置、日志/诊断
- 验收：导入后数据可读、关键任务可继续；安装包在干净 Windows 上启动。

## 验证流程（每阶段）

1. 离线/合成测试（不调用真实模型）
2. 隔离数据目录 + 空闲端口/独立应用实例跑通
3. 桌面安装包冒烟
4. 记录真实验证与未验证部分，不夸大
5. 提交到 Gitea（新仓库待定，建议 `dev/meeting-room-dsh`），每版一个提交

## 风险与对策

- **DSH 开发者预览、breaking changes**：固定 base commit，适配层隔离；不追每个上游。
- **Cordis 插件学习成本**：先 spike 两个页面，再扩大。
- **多 Agent 编排**：DSH 是单会话循环；编排服务独立，先串行，后并行。
- **Electron 打包自定义插件**：spike 验证；不行则改 Web 版 + 本地服务。
- **数据迁移**：先导出 JSON，单次导入；不双写；保留旧应用回退。
- **许可与品牌**：DSH MIT；不复制 Marvis 资产；产品命名与 UI 自研。

## 阶段 0 环境准备

- 先跑通 DSH 自带 Web/桌面，再在其上建插件分支 `meeting-room`；文档已在 `docs/meeting-room/`。
- Spike 记录：页面扩展点、两 Agent 轮次、MCP 调用、Electron 打包的实测结论与阻塞项。
