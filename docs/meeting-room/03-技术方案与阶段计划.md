# 技术方案与阶段计划

## 架构总览

```
DSH 桌面/Web（Electron + Web UI）
├─ 会议插件（本产品）
│  ├─ host 服务（Cordis 插件）
│  │  ├─ 领域服务：项目/团队/角色 Agent/会议/任务/验收/预算/评价
│  │  ├─ 编排服务：会议状态机、任务调度、主助手编排
│  │  └─ 存储：领域状态与索引（SQLite）；会议内容以 DSH 会话事件为准
│  └─ client UI（插件页面）
│     ├─ 主助手（对话 + 运行时间线）
│     ├─ 会议列表/详情
│     ├─ 任务/验收
│     ├─ Agent 库
│     └─ 技能/MCP
├─ DSH 能力（复用）
│  ├─ 会话/Agent 循环、工具执行、沙箱/审批
│  ├─ 模型适配器、MCP、技能扫描
│  └─ 设置/凭据/插件管理与市场
└─ 模型来源：Magpie / 原生 Codex / Claude / OpenCode Go / 直接 API
```

## 关键设计

- **插件而非 fork 核心**：会议业务作为 DSH 插件 + 客户端 UI 包，尽量不修改 DSH 核心；上游可更新。
- **编排模型**：一场会议 = 一个根会话，角色的一轮 = 该会话下的子代理运行；主助手会话负责拆解与创建会议。首轮隔离由编排层保证——首轮必须走 spawn 语义的子代理（`inheritsParentContext: false`，只收到任务文本），不能用 fork 语义（会带上父会话已完成轮次）。Stage 0 验证插件能否创建并关联独立根会话，失败则降级为主助手会话下的会议子代理树。
- **治理在服务端**：独立首轮、争议台账、终审/发布门槛由代码保证，模型不能绕过。
- **存储分工**：会议发言、轮次结果、裁决文本写成会话事件（模型可见 ⟺ 可重建）；插件 SQLite 存项目/任务/预算/验收/评价等领域状态与索引，便于列表查询与导出。
- **审批分两层**：工具/命令/MCP 调用走 DSH 审批（`ctx.approval.request` 或 `tools/pre-execute` 返回 `ask`，只支持 `allowed-once`，没有记忆授权）；预算批准、交付验收、返工由插件审批实体与页面处理。

## 数据模型（初稿）

- project: id, name, directory, background, management, budget
- agent: id, name, kind(role/capability), shell/model, prompt, permissions, roles, skills, disabled
- team: id, project, type, name, members, leader
- meeting: id, project, title, requirement, materials, status, stage, members, plan_versions, session_id
- round: id, meeting, index, stage(independent/discussion/synthesis/final), participants, state, started_at, finished_at
- meeting_message: id, meeting, round, agent, role, content_ref(会话事件 id), state, timing, usage
- objection: id, meeting, round, author, target, claim, status(open/upheld/rejected/deferred), verdict, rationale, decided_by, decided_at
- decision: id, meeting, round, kind(synthesis/final), author, content_ref, published_at
- task: id, project/meeting, title, requirement, acceptance, members, status, calls_used/max, artifacts, checks, error
- artifact: id, task, relative, sha256, bytes, format, accepted
- approval: id, scope(project/task/tool), action, requester, status, decided_by, decided_at, evidence
- budget_request: id, project, calls, reason, status
- rating: id, task, agent/team, scores, evidence, final
- skill: id, name, description, requires, instructions
- mcp_server: id, name, transport, command/url, tools(allowlist), enabled

## 阶段计划

### Stage 0：Spike（2～3 天）

只回答三个会改变方案的问题，外加一个两页 demo。

1. **首轮隔离与会议根会话**：开启 Team 模式确认子代理树与共享任务板可用；插件创建（或关联）会议根会话，用 2 个角色子代理各跑一轮首轮，写回会议详情与任务板。**判据**：抓取第二个子代理的模型请求，其中不含第一个的初稿；重启后轮次与发言仍可读。
2. **打包与持久**：打 Electron 安装包；在 `$DSH_HOME/profiles/desktop/cordis.patch.yml` 插入指向插件 checkout 的行（checkout 需先 `pnpm install` + `pnpm run build`），或用 `dsh plugin --profile desktop add <绝对路径>`。**判据**：干净桌面上安装启动，插件加载且会议与任务数据在下次启动仍存在。
3. **MCP 与审批**：用 `mcp-manager` 的 `servers` 配置注册一个文件类 MCP 工具（工具名形如 `mcp__<server>__<tool>`），发起一次写文件调用，先拒绝、再放行。**判据**：会话日志里 `approval/asked` → `approval/decided` 与对应 `tool/call` 的 `callId` 配对；拒绝后目标文件不存在。

顺带完成两页 demo（主助手页、会议列表/详情，假数据，复用 Conversation 渲染扩展点）；demo 可顺延到 Stage 1 首日，不影响上面的判据。

**分级回退**：①失败 → 降级为主助手会话下的会议子代理树；②失败 → 降级为 Web + 本地服务，插件与领域逻辑保留；③失败 → 能力 Agent 暂缓，先做纯会议治理。三项全失败才回退"现有会议室 + MCP/技能"混合路线。

### Stage 1：会议插件 v1（约 1～2 周）
- 项目/角色/团队/会议/轮次/意见/决策的存储与服务
- 会议状态机：独立首轮 → 讨论 → 综合裁决 → 独立终审 → 发布
- 主助手拆解并创建会议、收集结果
- 验收：一场完整会议可创建、推进、暂停/恢复、终审、发布；重启不丢；离线测试覆盖。

### Stage 2：任务与验收（约 1～2 周）
- 任务看板、执行（DSH 工具）、审核/验收/返工、产物登记、预算
- 业务审批：预算批准、交付验收、返工用插件审批实体与页面；工具权限仍走 DSH 审批
- 运行时间线与 L2 审批；失败/超时原因可见
- 验收：合成任务从创建到验收跑通；文件指纹与检查证据；预算不超。

### Stage 3：技能、MCP、角色库（约 1～2 周）
- SKILL.md 导入/分配/路由；MCP 服务器管理（含 Magpie hub）；能力 Agent（文件/搜索/浏览器）
- 预置角色 Agent 模板与默认权限
- 验收：导入 3 个技能、分配生效；MCP list/call；权限拒绝可见。

### Stage 4：迁移与交付（约 1 周）
- 现有会议室 SQLite 导出 → 新 schema 导入（项目/Agent/团队/讨论/任务）
- 旧应用保留为回退；桌面安装包、设置、日志/诊断
- 验收：导入后数据可读、关键任务可继续；安装包在干净 Windows 上启动。

## 验证流程（每阶段）

1. 离线/合成测试（不调用真实模型）
2. 隔离数据目录 + 空闲端口/独立应用实例跑通
3. 桌面安装包冒烟
4. 记录真实验证与未验证部分，不夸大
5. 提交到 Gitea（新仓库待定，建议 `dev/meeting-room-dsh`），每版一个提交

## 风险与对策

- **DSH 开发者预览、breaking changes**：固定 base commit，适配层隔离；不追每个上游。
- **Cordis 插件学习成本**：先 spike 页面与会话创建，再扩大。
- **多 Agent 编排**：DSH 是单会话循环；编排服务独立，先串行，后并行。
- **Team 的边界**：成员共享一个 checkout，不隔离工作目录，不跨进程，也不自动释放任务负责人；并行执行需插件侧显式分配工作目录与负责人。
- **Electron 打包自定义插件**：spike 验证；不行则改 Web 版 + 本地服务。
- **数据迁移**：先导出 JSON，单次导入；不双写；保留旧应用回退。
- **许可与品牌**：DSH MIT；不复制 Marvis 资产；产品命名与 UI 自研。

## 阶段 0 环境准备

- Node ≥24.9（DSH 要求）；pnpm 未安装时用 `corepack enable` 或 `npm i -g pnpm`。
- `pnpm install` + `pnpm run build` 后，`pnpm dsh web` 或桌面 `pnpm dev` 启动。
- 先跑通 DSH 自带 Web/桌面，再在其上建插件分支 `meeting-room`；文档已在 `docs/meeting-room/`。
- Spike 记录：会议根会话创建/关联、首轮隔离证据、MCP 审批、Electron 打包的实测结论与阻塞项。
- 桌面加载自定义插件两条路：`$DSH_HOME/profiles/desktop/cordis.patch.yml` 插入绝对路径或 `file://` 行（HMR 生效，无需 bundle patch）；或 `dsh plugin --profile desktop add <绝对路径>`（需 bundle patch 与 `dsh.bundle.patch`）。两条路都要求 checkout 先构建，插件的 DSH 版本要求需与打包运行时匹配。

## 待定问题

- Gitea：已建 `dev/meeting-room-dsh`（private），分支 `meeting-room`；后续版本在此提交。
- 插件代码放置：DSH 仓库内 `packages/plugins/meeting-room` 还是独立产品仓库依赖 DSH？（先仓库内插件，验证后再定）
- 主助手与会议的关系：主助手直接创建会议，还是先给用户确认会议计划？（建议先给一个可编辑的会议计划，确认后启动）
- 能力 Agent 的实现：DSH 原生工具、MCP 服务器，还是插件内工具？优先 MCP。
- 会议根会话的创建方式：插件能否直接创建并关联独立会话，还是只能从子代理树起步？Stage 0 出结论。
