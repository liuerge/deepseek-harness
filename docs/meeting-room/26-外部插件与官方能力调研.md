# 外部插件与官方能力调研：数字员工团队的取长补短

本页汇总第 10 轮调研的三路结果：DSH 生态第三方插件全量扫描、官方仓库未充分利用的能力盘点、非 DSH 开源实现与产品设计的机制参考。目的是回答「用户的数字员工团队工作台还能从外部补什么」。

调研由三个子 agent 并行完成（模型 `hy4-flash`），主 agent 独立复核了所有关键结论所依赖的源码事实。

## 结论速览

三路调研（DSH 生态插件扫描 / 官方仓库能力盘点 / 非 DSH 机制参考）串起来是一条决策链：

| 缺口 | 生态有无现成实现 | 能否整体换用 | 该怎么拿 | 决策 |
|---|---|---|---|---|
| ① 模型回退链 | 有（`dsh-fallback-models` v1.0.1、`dsh-model-fallback` v0.5.2，**npm 实存**） | 换用可行 | 这两个是**唯一**不改官方文件、不包装官方 API、不自建存储的，直接装即可；回退链的算法抄 Claude Code 的「来源优先级 + allowlist 逐级回退」。注意 `dsh-model-fallback` 默认**不切额度/鉴权类错误**（需改 `codes`），而用户当前最痛的正是 402 → 反而是 `dsh-fallback-models`（失败码含 `QUOTA`/`ACCOUNT_QUOTA`）更对症 | **装插件 + 抄算法** |
| ② 额度隔离 | 有（`dsh-agent-budget` 做并发安全预算预留） | 换用会双真相源 | 用**官方** `LlmConfigurableProvider.settingsNs` 让不同路由配不同账号；`dsh-agent-budget` 只借鉴它的「全局预留 + CAS 扣减 + 事务落账」 | **自建，借数据模型** |
| ③ 推理档位 | 有（`dsh-fallback-models` 已含 per-preset 档位） | 可换用 | 官方 `ctx.llm.resolveModelInfo().reasoning.efforts[]` 就能枚举档位；用户 `connections()` 现在把档位信息丢掉了，补上即可 | **用官方 API** |
| ④ 任务看板 | 有（`dsh-kanban-flow`、`dsh-agent-board`） | 换用会双真相源 | 借鉴 Linear/Jira 的**状态分组 + 允许转移矩阵**；返工**不加第 6 列** | **借数据模型** |
| ⑤ 团队插件 | 有（`dsh-swarm-orchestrator` v0.6.34 **npm 实存且兼容本地**） | 换用会双真相源 | `dsh-swarm-orchestrator` 把角色级模型固定 + 有序 fallback 链 + **per-role effort ladder** + `reviewGate:"human"` + 并发预算 + attempt 上限做全，机制最全；`dsh-agent-team-gui` 机制好但 **peer 声明装不上 0.2.2-rc.5** | **借机制（重点参考 swarm）** |
| ⑥ 审批质量门禁 | 有（`dsh-agent-quality-gates`、`dsh-agent-crew`） | 换用会双真相源 | 借鉴 Critic/Verifier 分离 + **unverifiable 硬门禁**（用户已有该状态但没升级为硬门禁） | **借机制** |
| ⑦ 任务书 + 上下文隔离 | 有（`dsh-agent-skills`、`dsh-plan-skill`） | 可部分换用 | 借鉴「计划是硬约束 + 阻塞项归档」；上下文隔离按角色定制 | **借机制** |

### 最终决策矩阵（catalog + npm + GitHub + dsh.pub 四层交叉后）

> **同名不同包警示**：`dsh-taskboard` 有**三个**不同来源——`cloader/dsh-taskboard`（npm v0.10.0）、`@shengsheng/dsh-taskboard`（npm v0.1.9，本表首选）、`shengsheng90/dsh-taskboard`（GitHub）；`dsh-fallback-models` 有 unscoped 与 `@soffits` 两支；`dsh-model-fallback` 有 unscoped 与 `@carl2003` 两支。装错包行为完全不同。

**两条「空白」的最终修正口径**（比「完全空白」更有用）：
- ②按 Employee 分桶的**花费**额度池：全生态唯一命中 `dsh-team-conductor`，但它是**成员级上下文 token 预算**（非花费额度池）且 npm 未发布 → 花费额度池仍须自建，成员容量/上下文预算可借
- ⑥read 事件交叉核对：`dsh-plugin-verification` 是**同构思想**、`dsh-spend-audit` 是**确定性重放对账范式**、`dsh-safe-workflow` 的 `audit.jsonl` 是 append-only 证据账本 → 「不信任自报」成熟可抄，「read 事件交叉核对证据路径」这一具体形态无可安装现成件

**总体判断**：
- 生态**机制层没有空白**（七个缺口都有现成实现），但**没有一个能整体换用**，因为它们都自建 SQLite + 状态机，会与用户的 `meetings.sqlite` + Employee/Team 形成双真相源
- 但**「能装」与「机制存在」是两件事**：全量 11979 条目录里只有少数包在 npm 真实存在，且精确匹配本地 `0.2.2-rc.5` 的只有 `@alpacachen/dsh-kanban` 一个。**②额度隔离与⑦上下文隔离在「可安装的插件」层面接近空白**
- 因此：**能装的就装（省事），装不上的把机制抄进用户自己的插件（保住数据模型与治理）**
- 唯一「零冲突、可直接装」的是**回退类**插件（`dsh-fallback-models`、`dsh-model-fallback`，走 `agent/request-error` 瀑布 + `agent.model.select()`，不改官方文件）——但目录条目里**大量插件查无此包**，上表已逐一 `npm view` 验证，别按目录站清单直接排期
- 其余全部**只借鉴机制**，落地尽量用**官方原生 API**，保持零第三方依赖 → upstream 滚动升级风险归零
- 用户当前有 **1 个高危授权漏洞**（员工路由绕过 Host 授权）与 **3 个静默失效/信息丢失问题**，见下文「隐藏风险」

**定稿说明**：本次调研经四轮迭代收敛（目录抽样 → 全量 catalog → 三层交叉 → 四源交叉）。上表所有 npm 包均已 `npm view` 实拉核对版本与 engines，所有 GitHub 包均已直查确认存在（HTTP 200）。**「可装」与「机制存在」是两件事**：目录站与 catalog 的收录口径都不能当全集，最终以 `npm view` + 仓库直查为准。

**检索方法学（四层交叉，重要）**：目录**不是全集**。必须「catalog(11979) + npm 全库 + GitHub 仓库直查 + `dsh.pub/api/plugins`(15028，独立数据源)」四层并用——
- 只查 catalog 会漏：`dsh-worktable`、`agentrq`、`dsh-task-memory` 三者 catalog 与 npm 均未收录，但 GitHub 直查全部存在（已复核 HTTP 200），口径应为「存在，需 GitHub 直装」

### 返工的会话续跑：resume 语义的四个结论

用户返工时员工是**全新会话**（`project-tools.ts:239` 每次 `startActivation`），只能拿到 handoff 摘要 + 失败验收报告。为此专门查了 OpenHands 的 `task_id` resume 语义（四个问题逐一核实）：

1. **resume 加载完整对话历史，不是摘要**。OpenHands 把它定义为「换 agent / 换模型重启同一任务」——本地 Agent 保留完整事件流继续，外置 Agent 从 `task_id` 拉回历史重建上下文，模型不记得但事件在。 → 用户对应：返工应复用上一轮 worker 会话（`activation.childId`），而不是新建。
2. **不清理状态**。源码确证：workspace 是 `parent_conversation.state.workspace.working_dir`，resume 时原样传入，**没有任何 reset / checkout / clean 动作**——上轮 agent 写了一半的文件留在原地，下一轮在**脏工作区**上继续。失败工具调用与错误消息同样保留在重载的事件流里。唯一清掉的是内存里的 conversation 句柄（`_evict_task` 置 `conversation: None`），**磁盘持久化不动**，resume 时从磁盘重建。 → 用户对应：交付物文件**保留**（员工要基于它改），但不能因此认为它已被接受；脏工作区语义与用户的 `cwd` 复用天然一致。
3. **OpenHands 没有区分「重试」与「返工」**。源码确证：`TaskStatus` 只有 `RUNNING / COMPLETED / ERROR` 三个值，**没有 rejected / rework / retry 状态**；`Task` 模型字段只有 `id / status / conversation_id / result / error / conversation`，**没有 attempt 计数、没有 rework 上限、没有 verifier 概念**；`max_turns` 字段已废弃。`task_id` 本身是纯序号计数器 `f"task_{n:08x}"`，不含 attempt 语义。resume 是无限循环的，靠 `_evict_task` + 磁盘持久化保证状态，而不是靠次数封顶。 → 用户对应：**这条是用户独有的**。用户已有 `rework.maxAttempts`，正是 OpenHands 缺的封顶语义，不要换成它的 resume 主路径。落地应是：
     - **重试**（瞬时失败）→ 复用会话 + 重发指令
     - **返工**（验收驳回）→ 复用会话 + **新审核人**重审，但**不应把上一次的 `passed:false` 报告喂给员工**（否则锚定在错误方案）
4. **resume 的预算是「单轮内」预算，不是「跨轮返工」预算**。`max_budget_per_run` 从 agent definition 或父会话继承；resume 时沿用 conversation 持久化里已有的计数，**不重置**。父侧 metrics 是**替换而非累加**（注释原文：*"Replace (not merge) because sub-agent metrics are cumulative across resumes"*）——因 `task.id` 不变，多轮 resume 的花费最终是累计值，但父侧**看不到「这轮 resume 花了多少」的拆分**。 → 用户对应：需要「每员工额度 + 每任务预算」两级账，且能看清单轮消耗——OpenHands 的记账粒度不够，仍需在 DSH 侧自建。

**对用户的直接结论**：用户现有 prompt（`project-tools.ts:228`）把「Repair assignment + Failed independent acceptance」整段喂给员工，正是上面第 3 点要避免的「锚定在错误方案」。建议改为——返工时给员工**上一轮的产出与失败现象**（文件路径、实际检查输出），但**不给审核人的裁决结论**；裁决留在新一轮审核人手里。

### 三种「续跑」语义必须先选一个

不同实现对「返工时员工看到什么」的答案完全不同，选错了会返工到错误的上下文上：

| 语义 | 代表实现 | 员工看到什么 | 适合什么 |
|---|---|---|---|
| **A. 重载完整历史** | OpenHands `task_id` resume | 完整事件日志重载（含上轮失败的工具调用与错误消息），长会话会被 Condenser 压成摘要 | 上下文连贯优先；但长会话下看到的是压缩版 |
| **B. 同一 attempt 内注入** | DSH 生态 `dsh-agent-crew` 的注入式 | 驳回内容作为消息注入**活着的会话**，不重载历史 | 轻量；会话已开着时最自然 |
| **C. 开新 attempt** | Vibe Kanban 的 attempt 机制 | 旧 attempt **封存**，开一个**新 attempt**（可换 agent / 可换 prompt / 预算独立），历史只在报表里 | 要做 attempt 级报表、预算隔离、返工率统计时最合适 |

**用户的选法建议：模型回退用 A，返工用 B**——返工时复用同一 worker 会话并注入结构化的失败现象（不给裁决结论），预算与 attempt 计数由宿主侧 `project_records` 负责记账。若将来要做「返工率」「每 attempt 成本」报表，再把记账维度升级成 C，但不必现在就把会话切掉。

### veto 机制：审核人否决不该是「返工」

调研中一个反复出现的模式（`dsh-agent-crew` 的审批卡、`dsh-model-router` 的 `reviewGate: human`、`dsh-swarm-orchestrator` 的 `reviewGate: "human"`）是：**审核人的否决是一个显式的人工闸门，不是一条自动重试边**。`dsh-agent-crew` 明确写「Nothing irreversible happens without you. Every send, post, purchase, delete, merge or booking waits for your click on an approval card」。

对用户的意义：当前设计里「审核人判不通过 → 自动进返工 → 重跑」，把**质量判定**与**人工裁决**混在了一条线上。建议区分：

- **返工**（自动）：机器可判定的失败——测试没跑过、证据缺失、产出不合格 → 同一员工带着失败现象重跑，消耗 attempt
- **veto**（人工）：需要人拍板的否决——需求本身错了、方向要改、该换人做 → **停在受阻列等人**，不自动重跑

这样 `release: 'human'`（用户已有的第三种 release 模式）就有了更清晰的对位：release=human 的任务，审核人否决即进 veto 而不是进返工。

## 四、用户的隐藏风险（源码复核）

### 一个被外部报告误判、但源码核实后**对用户不成立**的「宿主硬约束」

外部调研提出：「`Employee` 无法做成跨会话常驻实体，子代理的模型来自会话的模型选择器而非插件侧传参，因此生态里三个同类插件（`dsh-staff` / `dsh-team-employees` / `dsh-company`）全部妥协为『Employee.model 只作备注』」。

**源码复核结论：这条对用户的实现不成立。** 三处证据：

1. **parent 校验用户已满足**。`packages/subagent/subagent/src/index.ts:274-277` 确实要求 parent 是「此刻活着的那个 Agent 实例」（对象同一性校验）：
   ```ts
   if (this.ctx.get('agents')?.get(spec.parent.id) !== spec.parent) {
     throw new SubagentError('subagent creation requires the exact live parent agent', 'UNAUTHORIZED')
   }
   ```
   但用户的 parent 是 `exec.agent`（`meeting-room/src/project-tools.ts:69`）——**就是当前调用工具的那个活实例**，天然满足该约束。用户不是「跨会话复用员工实例」，而是「Employee 档案持久化 + 每次在当前会话内实例化」，本就是两层模型。

2. **员工级模型路由确实生效**。`packages/subagent/subagent/src/manager.ts:340` 是 `resolveChildAgentOptions(parent, spec.agentOptions, childDepth)`，随后 `agentProvider`/`agentModel` 直接取自解析结果；而 `packages/subagent/subagent/src/child-agent.ts:108-116` 的解析顺序是「先铺继承值、**再 `...requested` 覆盖**」——用户传的 `{ provider: employee.provider, model: employee.model }` **完整覆盖**父会话的模型。

3. **同一处代码正是档位静默清除的来源**。`child-agent.ts:117`：`if (routeChanged && requested?.reasoningEffort === undefined) delete resolved.reasoningEffort` —— 用户改了员工模型、但员工档案没有档位字段，档位就被静默丢掉。这与上文「建议 3 / 建议 6」是同一处代码的两面。

**但有一条能力约束要写进已知约束清单**：路径 B 传 `agentOptions` 会触发 `assertCapabilities`（`subagent/src/index.ts:588`：`{ when: request.agentOptions !== undefined, cap: 'agentOptions' }`）——后端若不支持 `agentOptions` 能力，会抛 `UNSUPPORTED_CAPABILITY`。当前本地 in-process provider（`subagent-spawn-in-process/src/index.ts:40`、`subagent-fork-in-process/src/index.ts:62`）都声明 `agentOptions: true`，所以**用户现在的用法不会踩**；但若日后把 worker 换成 ACP / Codex / Claude Code 后端就会失败。这与路径 A 的前置条件 ③ 是同一个能力位。

**结论**：外部报告指出的「Employee.model 只作备注」是**归因错误**——不是宿主不允许，而是**那三个插件自己没开 `modelSelection`**，也没用直连 `agentOptions` 路径。宿主两条路径都支持指定子代理路由：

| 路径 | 谁能定路由 | 三个前置条件 |
|---|---|---|
| **A. `tool-subagent` 工具参数路径**（模型在工具调用里传参） | 模型 | ① 委派工具实例须配 `modelSelection: true`（**默认 false**；官方 preset 里 Web/Desktop 开了 discovery 与 route 字段，**headless/SDK/ACP profile 不开**）② Host 的 `/model-selection-settings` 服务（`ctx.subagentModelSelection`）须已挂载并授权 route 白名单，否则只允许继承父 Agent 当前模型 ③ 后端须支持 `agentOptions` capability（in-process Spawn/Fork 与 DSH SDK 合格；ACP/Codex/Claude Code 挂不上） |
| **B. `ctx.subagents.startActivation({agentOptions})` 直连**（插件宿主传参） | 插件宿主 | 无上述前置条件，但**不走 allowlist 校验**（见建议 2） |

**关键区分：这是「按次委派」而非「实体绑定」**——每次派活都要重新传参。所以 Employee 档案里的 model 语义应是「**派活时该传什么的默认值**」，而不是「常驻在员工身上的绑定」。这个语义差别正是外部插件显得「做不到」的原因。

**真正成立的硬约束只有一条**：跨会话常驻的 Employee **实例**在插件层做不到（live parent 对象同一性校验）。但用户本就不需要常驻实例——需要的是**档案持久 + 每次在当前会话实例化**，这正是路径 B。

**因此用户当前实现方向是对的**——不需要改成「员工级模型只作备注」，但要补两件事：① 档位显式存档 + 路由变更时剥离而非静默清除；② 会话切换时的工位三态与交接单（见建议 7）。

**另需注意**：路径 A/B 都只解决「派活时静态指定」，**不解决执行中按难度或失败动态切档**——那仍需 `dsh-agent-board` 的力度路由或 `dsh-fallback-models` 的失败回退链来补。

**可借鉴的三条配套机制**（来自那三个插件的设计）：
- **工位三态** `online` / `missing`（名册绑了名但会话里找不到它）/ `unbound`——用户 Employee 必然遇到「档案在但本次会话无人接活」，这套三态语义可直接借用
- **交接单**（`dsh-staff` 的 `staff_rebuild`）：跨会话时把 Employee 还原成 spawn 参数重建
- **自动派活默认关闭 + 显式开启 + 每日上限**（`dsh-staff` 的 `staff_autopilot`）——「自动唤醒 = 自动计费」，这个默认值取向值得抄
- **判别「谁能批准」**：生态里用的是宿主内部字段 `exec.agent`（`dsh-team-employees` 明确说这是目前唯一能区分人 vs 员工的手段，并提醒升级后重跑自检）。用户若做同类区分，**必须加宿主升级自检**，因为它是内部字段

### 其余风险清单（源码复核）

## 五、落地建议（按性价比排序）

### 建议 1：给 provider 配上 `ACCOUNT_QUOTA` 重试码（极小，零代码）
只改 `cordis.patch.yml` 的 provider 配置，让额度错误进入重试路径。这是「额度隔离」的前置——**先能重试，再谈切换到哪个账号**。

现状实测（`opencode-go` 通道全部不可用）：
```
deepseek-v4.1-flash  HTTP=402  Insufficient balance
deepseek-v4-pro      HTTP=402  Insufficient balance
minimax-m3           HTTP=402  Insufficient balance
hy4-preview          HTTP=400  Model is unavailable
hy4flash             HTTP=400  Model is unavailable
```
同期 `api.deepseek.com` 直连 `HTTP=200` 正常。这组实测正说明「同账号多模型」不等于「有额度」。

### 建议 2：接入官方授权预检（中，堵授权漏洞）

**先厘清宿主的两条独立路径**（这是最容易搞混的地方）：

| 路径 | 谁能定子代理路由 | 走 allowlist 校验？ | 用户走哪条 |
|---|---|---|---|
| **A. `tool-subagent` 工具参数路径** | **模型**在工具调用里传 `provider`/`model`/`reasoning_effort` | ✅ `model-selection.ts:146` 调 `assertAllowedModelSelection` | ❌ 没用 |
| **B. `ctx.subagents.startActivation({agentOptions})` 直连** | **插件宿主**传 `agentOptions` | ❌ **完全不校验** | ✅ 用户走这条 |

路径 B 的实际链路（已逐行核实）：`manager.ts:340` → `resolveChildAgentOptions(parent, spec.agentOptions, childDepth)`（`child-agent.ts:99-118`）→ 解析顺序是「先铺父会话继承值，**再 `...requested` 覆盖**」，所以用户传的 `{ provider: employee.provider, model: employee.model }` **完整生效**——但也**完全不受 `subagent-model-selection` 的 `allowedModels` 白名单约束**。

`modelSelection` 开关（`tool-subagent/src/index.ts:86`，默认 `false`）只管路径 A，且**预置里没有任何 bundle 打开它**（`packages/bundle/*/cordis.patch.yml` 与 `packages/preset/*/cordis.patch.yml` 搜不到 `modelSelection`）——也就是说宿主当前的默认状态是「模型不能自己选子代理路由」。

**因此修法是：在路径 B 上自己补校验**，而不是去开 `modelSelection`（开了也不能约束用户的直连）。

**配置语义（`model-selection-settings.ts` 逐行核实，决定怎么接）**：
- `enabled` 与 `allowedModels` 都带 `.volatile()` 标记（`:32-35`）——**每次委派实时采样**，改完立即对所有 Session 生效，不进持久化 profile 配置
- `allowedRoutes()`（`:47-56`）的语义要分三种情况：
  - `enabled` 为 **false** → 返回 `undefined`，**完全不读也不校验路由**。这是宿主默认状态（`:32` 的 `default(false)`），此时用户路径 B 不受任何约束
  - `enabled` 为 **true** 但 `allowedModels` 为空 → **抛 `INVALID_MODEL_SELECTION_SETTINGS`**（`:54`）。**这是个踩坑点**：用户若只想在自己的插件里校验名单，却先去开了 `enabled`，会因为白名单空而炸
  - `enabled` 为 true 且名单非空 → 返回副本列表，此时路径 A 才会用 `assertAllowedModelSelection` 强制约束

**具体落法**：
- 用户**不必**去动 `enabled`——那是给「模型自己选路由」用的开关，与路径 B 无关。正确做法是在用户自己的插件里读 `allowedRoutes()`：**返回 `undefined`（未启用）时按「不限制」处理并放行**，返回列表时才校验；**不要自己抛那个 `INVALID_MODEL_SELECTION_SETTINGS`**，那是宿主的语义，用户侧应跳过而非报错
- `roster-management.ts` 保存员工时：拿 `allowedRoutes()` 的结果（列表或 undefined），列表存在且不含该员工路由 → 拒绝保存并回报可选项
- 三处派发点（`index.ts:244`、`project-tools.ts:245`、`acceptance.ts:126`）在 `startActivation` 前调 `preflightChildLlmRoute(ctx.llm, parentOptions, { provider, model }, signal)`，让路由与档位在派发前就被校验
- 引入路径注意：`model-selection.ts` **没有编译产物**（`lib/` 下只有 `index.js` 与 `model-selection-settings.js`），但包 `files` 含 `src` 且导出通配 `./src/*`，所以走源码路径 `@deepseek-ai/dsh-tool-subagent/src/model-selection.ts`
- `roster-management.ts` 保存员工时：读 `subagent-model-selection` 命名空间的 `allowedModels`（`packages/subagent/tool-subagent/src/model-selection-settings.ts:27`，是 `Volatile` 设置支持热读），用 `assertAllowedModelRoutes()` 校验；名单非空且不含该员工路由 → 拒绝保存并回报可选项
- `project-tools.ts:239` 派发前：调 `preflightChildLlmRoute(ctx.llm, parentOptions, requested, signal)`
- 引入路径注意：`model-selection.ts` **没有编译产物**（`lib/` 下只有 `index.js` 与 `model-selection-settings.js`），但包的 `files` 含 `src` 且导出通配 `./src/*`，所以走 `@deepseek-ai/dsh-tool-subagent/src/model-selection.ts` 源码路径引入

### 建议 3：员工档案加「推理档位」+「回退链」（中，官方原生）
- `roster.ts` 的 `employeeSchema` 加 `reasoningEffort` 与 `fallbackRoutes`（有序数组）
- `roster-management.ts` 的 `connections()` 现在只取 `model.id`/`model.name`，需补 `resolveModelInfo()` 的 `reasoning.efforts[]` 才能渲染档位下拉（候选必须来自模型自身声明，不能硬编码）
- 三处注入点（`index.ts:244`、`project-tools.ts:245`、`acceptance.ts:126`）统一改为读员工档案的路由链
- 回退链算法抄 Claude Code 的「来源优先级 + allowlist 逐级回退」，用官方 `agent.model.select()` + `agent/request-error` 瀑布实现

### 建议 4：额度隔离（中，用官方多命名空间）
`LlmConfigurableProvider` 的 `settingsNs`/`settingsPath` 让不同 provider 路由配在不同 settings 命名空间、各自独立 `apiKeyEnv`。落法：员工档案加「额度池」字段（指向某个 provider 路由 id），主助手与员工用不同路由 → 不同账号。密钥用 `credentialRef('NAME')` 引用，不进配置文件。

### 建议 5：返工复用 worker 会话，并区分「重试」与「返工」（中，参考 OpenHands resume）
当前返工是**全新会话**（`project-tools.ts:239` 每次 `startActivation`），员工只能看到 handoff 摘要 + 失败报告。已查清 resume 语义（见上文专章），落法：

- **返工复用上一轮 worker 会话**（`activation.childId`），交付物文件保留，员工基于自己的产出继续改
- **区分两种语义**：
  - 重试（瞬时失败）→ 复用会话 + 重发指令
  - 返工（验收驳回）→ 复用会话 + **新审核人**重审
- **prompt 要改**：现在 `project-tools.ts:228` 把 `Failed independent acceptance` 整段喂给员工，会让员工锚定在错误方案。改为给「上一轮的产出与失败现象」（文件路径、实际检查输出），**不给审核人的裁决结论**——裁决留在新一轮审核人手里

### 建议 6：档位失效要「剥离而非静默降级」（小，抄 swarm 的做法）

`dsh-swarm-orchestrator` README 里有一条值得直接抄的规则：

> 派生子代理前，固定的推理档位会针对部署声明的模型能力做校验——**声明不含该档位的模型会被剥离 pin**，且候选链**不会**因此被过滤；完全不声明档位的模型则不做处理（缺失即未知，adapter 可能从它自己装的 catalog 里解析出来）。不兼容时用**同一模型**在 effort 梯子（`max` → `high` → …）的下一档重试，**在轮换模型之前**，且**不消耗任务的 retry 预算**。

这正好对上用户当前的静默失效问题：官方 `child-agent.ts:70-84` 在路由变更时会直接 `delete resolved.reasoningEffort`，用户完全无感。正确语义应是「显式剥离并记录」，而不是「静默消失」。

### 建议 7：员工「工位三态」与交接单（小，抄 dsh-staff）

用户 Employee 是持久化档案 + 会话内实例的两层模型，必然遇到三种状态：**本次会话有人接活**（online）、**档案在但本次会话没人接**（missing）、**完全没绑定**（unbound）。`dsh-staff` 的工位三态给了现成语义。

配合 `staff_rebuild` 的**交接单**思路：跨会话派活时，把 Employee 还原成 spawn 参数重建（名字、职责、模型、审核人配置），而不是试图复用上一次的子会话实例。

### 建议 8：返工回退到原状态列，不加第 6 列
生态横向结论（LobeHub / dsh-kanban-flow / dsh-agent-board 一致）：返工是**带警告的向后转移**，卡片回到「进行中」，attempt 历史记在卡片上，而不是进一条新的「返工中」列。用户的「受阻」列已经承担了「非终止自定义 state」的语义。

但用户的返工语义比主流更特殊：**「审核人判定交付不合格 → 退回复工」这条路径在所有被调研的框架里都没有对应实现**——主流把回退只挂在故障/额度上，验收驳回一律升档重写。因此：

- **模型回退链**（可用性语义）：故障/额度触发，横切同档模型，链尽才降档
- **返工链**（质量语义）：验收驳回触发，走 `rework.maxAttempts`，耗尽即阻断

两条链要**分开设计**，不要合并成一条"重试"逻辑。用户现有代码已经是分开的方向（`project-tools.ts:110-114` 单独算 `rework.attempt`），保持即可。
