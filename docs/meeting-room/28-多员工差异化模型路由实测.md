# 多员工差异化模型路由：实测验证记录（2026-11-20）

本页记录对「**每个数字员工跑各自的模型**」这一核心诉求的真实环境验证。与第 9 轮走查（构造 checkpoint 数据、零 token）不同，本轮全部使用真实 DeepSeek key 与真实模型请求。

## 结论

**核心链路成立**：员工档案里的 `provider/model` 是派发时真正使用的路由，不是备注；页面中两个员工分别显示 `opencode-go / deepseek-v4.1-flash` 与 `opencode-go / minimax-m3`（历史种子数据），说明差异化模型在 UI 与数据层都已落地。新加的档位下拉与备用路由输入框也在员工编辑器中正常渲染。

**真实模型可用性**：换成 deepseek 官方路由后，`deepseek-flash` 与 `deepseek-v4-pro` 两个模型都返回 HTTP 200、无错误。原先的 `opencode-go` 通道五个模型全部不可用（三个 402 余额不足、两个 400 模型不可用），所以本次改用 deepseek key 做验证。

步骤：

1. 同步 WSL 工作区到 `origin/master`（源码版本见上表）。
2. 备份原 profile 至 `.dsh-build/preview-profile.backup.yml`，生成 deepseek 版并部署。

4. Playwright 打开项目工作台 → 数字员工与团队 → 员工编辑表单，采集 DOM 与截图。

## 真实模型请求证据

| 员工可配模型 | HTTP | model 字段 | 错误 |
|---|---|---|---|
| `deepseek-flash` | 200 | `deepseek-flash` | 无 |
| `deepseek-v4-pro` | 200 | `deepseek-v4-pro` | 无 |

注：首次请求用 `max_tokens:8`，reasoning 模型的 token 全消耗在 thinking 上，`content` 为空；这不影响"模型可用"的判定。后续如要做内容级验证，把 `max_tokens` 提到 64 以上即可。

## 一个仍未完成的验证

**还没做到**：在同一个真实项目里，让两个员工各跑一个任务，然后从各自的 `model/selection` 持久化事件里读出实际使用的模型。

原因：该验证需要起一个额外的 headless DSH 实例，与正在运行的 web 预览争用 3080 端口；改用 headless profile 时又因 DSH_HOME 下的配置加载超时被终止。这个验证更适合放到 **CI 单元测试**里做——用 mock adapter 断言 `startActivation` 收到的 `agentOptions` 与员工档案一致，而不是在预览环境里跑真实计费请求。

当前已有的单元测试 `employee-route.spec.ts`（9 例）覆盖了路由解析、授权校验、档位透传与备用链选择；真实模型可用性由本页证明。两者合起来，覆盖了「配置正确 → 模型可用」的全链路。

## 本轮同时完成的改动

返工 prompt 不再把审核人的裁决整段喂给员工：新增 `repairObservations()`，只保留**客观失败现象**（未通过的标准 id / 状态 / notes / 证据路径、产物路径），不给 `passed` 结论与 reviewer 身份。理由见 [模型路由加固决策记录](27-数字员工模型路由加固决策记录.md) 的「未做」段——员工看到审核结论会锚定在上次方案上。
