# 双助手并行开发分工

本参考用于将数字员工团队工作台的下一轮开发拆给两位开发助手。目标与验收基线继续以[产品目标](01-目标与产品定位.md)、[治理基线](11-项目治理与验收基线.md)和[近期实施顺序](12-开发任务拆解与里程碑.md#近期实施顺序)为准。本轮先分两路，最后集成验收。

## 分工与交付

| 负责人 | 工作范围 | 用户可观察的结果 |
|---|---|---|
| 当前主开发助手（A） | 多厂商模型连接目录、逐员工模型配置、团队配置及主会话团队模式入口 | 先配置不同厂商员工并保存团队，在团队模式选择已配置团队，下发需求，按确认计划组织执行和验收 |
| 用户另行安排的开发助手（B） | 已有 Team 任务关联、派发时序、冲突处理、关闭收尾与重试幂等 | 员工正确领取后才开始工作，人工改派不被覆盖，失败或取消不误报完成，重复请求不重复派工 |

A 负责整体产品语义、双方代码整合、多厂商真实联调及最终回归；B 提供可独立审查的后端修复与确定性测试。B 的交付不包含新的团队模式页面，也不代表整个产品已完成。

推荐 B 从当前已提交 HEAD 建立独立 worktree 并记录基线，避免同时构建时写入同一套产物。A 已有未提交的多厂商会议路由修改，B 不需要复制或回退这些修改即可开始。若共用工作目录，则除源码文件归属外，构建、生成器和预览进程也必须错开，不能同时改写 lib 或客户端产物。

## 可直接交给助手 B 的任务

你负责 DeepSeek Harness fork 中数字员工项目的 Team 派工可靠性，工作目录为 `D:\agentProjet\deepseek-harness`。请先阅读根 AGENTS.md、docs/architecture.md、docs/defensive-patterns/README.md、docs/testing.md，以及本目录治理基线和开发计划。涉及生命周期、并发测试及失败处理时，使用仓库相应技能。保留工作区已有修改，不重置、覆盖或提交其他助手的改动。

### 允许修改的文件

- `packages/experimental/meeting-room/src/team-link.ts`：Team 关联、领取、同步及完成规则。
- `packages/experimental/meeting-room/src/project-tools.ts`：项目执行的领取时序、在途操作跟踪和重复请求处理。
- 在 `packages/experimental/meeting-room/tests/` 新建名为 `team-dispatch-reliability.spec.ts` 的测试，以及该文件需要的专用测试辅助文件。优先使用现有真实 Agent/Team/Session 测试组合，避免仅模拟被修复函数的返回值。
- 新建 `docs/meeting-room/15-Team派工可靠性验收记录.md`：记录最终行为、实际执行的检查和未完成项。既有公共文档由 A 合并更新，避免并发编辑。

其他文件由 A 负责，尤其不要修改 `src/index.ts`、`src/dashboard.ts`、`src/roster-tools.ts`、`src/types.ts`、`src/store.ts`、原 `tests/meeting-room.spec.ts`、Client 包、模型提供者、公共 README 和现有规划文档。如确需修改共有类型、数据库或底座扩展点，先提出具体接口、理由及影响，由 A 协调归属后再实施；这属于开发协调，不需要用户重复批准既定需求。

### B1：保护人工改派与编辑

当前 `claimProjectTeamTask` 遇到其他负责人时会释放并接管；`completeProjectTeamTask` 读取最新版本后可能由主助手直接完成任务。需要区分项目合法返工换人、已经授权的同步，以及用户在看板上的改派、释放或内容变更。不能仅靠读取最新 revision 后执行 CAS，把此前发生的外部修改当成已确认状态。

验收：任务被人工改派或释放后，项目不抢回、不替新负责人完成、不放行下游；返回可定位任务的结构化冲突并保留现场。正常返工仍能从此前项目员工交接给新子会话；正常自动验收和人工放行续跑不退化。任务被删除或提前完成时仍有明确处理。

### B2：领取成功前禁止员工执行

当前项目先调用 `startActivation`，随后才领取 Team 任务。启动返回不等于子会话尚未执行，事后 dispose 也不能撤销已完成的工具写入。通过现有插件扩展点建立启动前的执行门控，不修改 agent-loop，不将领取失败后的取消当成启动前阻止。

验收：用明确的异步屏障挂起领取，在领取完成前模型请求及有副作用工具均为零；领取失败、取消或模式关闭后，仍无员工写入且不启动下游。成功领取后正常执行，作用于准确子会话，不阻塞无关员工。门控注册和等待资源在所有路径释放，不能出现取消死锁。

### B3：覆盖关联期间的卸载与取消

当前 `project_execute` 在 `linkProjectTeamTasks` 或 `syncReleasedProjectTeamTasks` 的等待结束后才加入 running 跟踪。需要让 drain 覆盖从首次异步操作起的完整执行，包括关联与同步阶段；存储必须在这些操作和子会话收尾结束后关闭。

验收：分别在创建关联、同步已放行节点及员工运行时挂起，再卸载插件；卸载等待相关操作收尾，所有启动的 Promise 均被观察并结束。不得晚写已关闭 SQLite、关闭后继续派工或遗留未处理拒绝。外部操作结果未知时保留可核查状态，不能自动认定为未发生。

### B4：已预留执行的并发重试

当前关联失败后可以复用已经预留、尚未记录 started 的执行，但两个同时到达的重试可能各自读取旧看板并重复创建或派发。修复同一 Host 实例内的并发重试，覆盖初次启动、部分关联失败和已预留执行再次请求。

验收：通过屏障同步两个请求，最终每个计划任务只有一个 Team 任务，只有一次员工执行；竞争请求明确返回正在处理或已领取结果。部分创建成功后的重试吸收原任务，不重造；异常退出释放本实例的临时占用。单进程锁不等于跨进程保证，跨进程崩溃恢复若未实现须如实列为限制。

### 需要保留的既有行为

员工使用已确认计划捕获的 provider、model、职责和可选 preset，不回退为统一主助手模型。Team 任务状态不能取代项目验收：失败、待人工确认和返工均阻断下游；新旧验收报告保留；人工节点不自动放行。未启用 Team 的既有执行保留其明确的未关联行为。所有新增模型可见信息必须可从 Session 日志重建。

### 测试与交付要求

先编写能够重现问题的回归，再修复。并发场景用 barrier 或明确事件同步，不用固定 sleep 碰时序。测试结束前等待所有工作结束、还原监听器并释放 Context 和数据库；不跳过失败测试，不降低全局规则。

执行新增测试、现有 meeting-room Host 与 Client 聚焦测试、改动文件 lint，以及最新 build:artifacts 后的 build:check。文档按仓库要求检查。只报告实际执行的命令和结果；Windows 环境阻碍时可以在 WSL 工作副本验证，分别记录两个环境的证据。本任务可用合成适配器，不需要发送用户背景或使用真实厂商密钥。

交付包含改动文件清单、B1–B4 逐项证据、结构化错误与恢复方式、未完成项，以及可审查 diff 或独立提交。不要推送、合并或替其他助手改代码。工作区已有未提交变更属于 A；只暂存自己负责的文件。如使用独立 worktree，保持可合并提交，不改写主工作区历史。

## A 的对应工作及集成顺序

A 负责复用既有模型提供者和凭据服务，实现员工连接与模型选择、保存团队，以及团队模式选择。员工/团队配置和 Team 运行开关是不同记录，需要建立明确关联；选择模板本身不确认计划、不授权无限执行、不替代工具审批。新会话选队、已存在主会话切换团队及确认后配置变更都需明确生效范围，模型可见选择必须进入会话记录。

开发期间按文件归属工作，B 可以先使用已有确认计划与 Team 测试组合，不等待配置页面。完成 B 的后端回归后，由 A 集成并核对入口选择、确认计划、实际工具交付、失败返工、独立重验和人工节点。最终再分别验证真实多厂商调用和界面，不把合成适配器测试等同于完整产品验收。
