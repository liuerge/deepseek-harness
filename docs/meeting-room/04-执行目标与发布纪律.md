# 执行目标与发布纪律

## 总目标

在 DSH 上把会议室做成可验收的数字员工团队：主助手接目标、开会、调度、交付，用户只做决策与验收。按 Stage 0 → 4 推进，每个发布节点的测试通过后才推送。

## 工作纪律

1. **测试先行于推送**：任何发布节点的代码或文档，先在本机跑完该节点要求的测试；未通过不推送。
2. **一次只推进一个发布节点**：未达节点通过条件，不开始下一个节点的实现（探针性 spike 除外，须在记录中标明）。
3. **全过程留痕**：每个工作日或每个节点，在[实施记录](06-实施记录.md)追加一条：做了什么、遇到什么问题、跑了什么测试、结果与证据、哪些没验证。
4. **计划变更先写文档再动手**：目标、阶段、验收口径变化，先改 01/03/04，再改代码。
5. **不夸大结论**：只写实际跑过的命令与实际输出，没跑就写"未验证"。
6. **提交粒度**：一个发布节点一组提交；修问题单独提交并写清触发原因。

## 每个节点的推送前检查

1. 该节点的测试清单全部执行，结果写入实施记录。
2. 失败项要么修复，要么在记录中标注为已知限制并说明影响范围。
3. 文档同步：受影响的 01/02/03 与记录页更新。
4. `git status` 确认没有误提交的临时文件、数据目录、日志。
5. 提交信息写明节点编号与测试结论。

pnpm run verify-md-links
