# 交互可供性约束与 Marvis 产品参考（2026-11-21）

本页记录两件事：一是用户指出的「向主助手提出调整按钮没有单元格底色、不容易突出可交互内容」的可供性（affordance）问题，审计同类问题后统一修复，并把规则提炼成可复用的约束；二是阅读 Marvis《多 Agent 体系》文档后，对产品设计（尤其过程透明）与测试验收方法的启发。截图存 `ui-review-20261121/`。

## 可供性约束（本次提炼）

问题根源：项目工作台的次级按钮全部使用 Button 默认 `ghost` 变体——静止态完全透明，只有悬停才出现底色。放在平面卡片上（摘要条、计划卡、看板卡、花名册列表行），静止态没有任何「可点击」的视觉信号，用户只能靠文字猜。

提炼出的变体使用约束（与 `dsh-client-ui-ux` 技能「选择组件角色与尺寸变体」规则一致，全部使用 Button 原生变体，未新增样式）：

- **平面卡片或列表行上的独立动作 → `outline`**（内嵌发丝描边 + 悬停填充）：静止态即可辨识可点击。适用：摘要条「向主助手提出调整」、刷新进度、计划卡「修改计划」、看板卡「查看会话 / 验收条件」、列表行同款按钮、待办区「返工 / 采纳旧计划」、花名册「编辑员工 / 编辑团队 / 委托团队 / 配置员工 / 配置团队」。
- **推进型主动作 → `primary`**：每个页面/卡片至多一个。适用：提出需求、确认此版本、按此版本执行、确认验收并放行、保存配置。
- **ghost 保留给**：取消类动作、工具栏内成组控件（全屏切换等图标按钮）。
- **走查要求**：新增按钮时对照本约束自查；走查脚本断言「静止态可辨识」纳入常规验收（截图 `56-可供性-摘要条与看板.jpeg`、`57-可供性-计划卡.jpeg`）。

修复范围：`ProjectPage.tsx` 12 处、`RosterEditor.tsx` 7 处按钮变体调整；构建门禁全过。

## Marvis《多 Agent 体系》的启发

**产品设计的对照**：Marvis 用「主 Agent 统筹调度 + 出厂预置角色化 Agent」回答"谁来干活"，用「你能实时看到的四件事」回答"过程透明"——当前执行到哪一步、哪个 Agent 在处理、中间结果是什么、最终产出在哪里。逐项对照我们的工作台：

| Marvis 的四件事 | 我们的对位 | 差距 |
|---|---|---|
| 当前执行到哪一步 | 看板按执行状态分列 + 列计数 | 已覆盖；「步骤序列」语义弱于 Marvis 的步骤清单，暂不采纳（列语义已定执行状态） |
| 哪个 Agent 在处理 | 卡片负责人头像 + 子会话「查看会话」 | 已覆盖 |
| 中间结果是什么 | 卡片 handoff 摘要（前 100 字）+ 详情面板完整交接与验收报告 | 已覆盖；handoff 可展开为独立可见性视图，待评估 |
| 最终产出在哪里 | 项目资产表（计划文档 / 约定产物 / 已核对产物带哈希） | 已覆盖 |

**测试验收的启发**：把「四件事」升级为验收 rubric——E2E 走查时**任何时刻**截取 UI，都必须能回答这四个问题，且答案可回溯（顺着中间结果追到结论，而不是只选择「信」或「不信」）。本次裁纸刀走查已隐式验证：执行受阻时四个问题都有答案（47/48 号截图）；后续走查把它写成显式断言。

**干预与信任的成对设计**：Marvis 明确「透明日志解决看得见，L2 硬垂询解决拦得住」。我们已有对位能力（会话轨迹 = 看得见；`ui-approval` 与验收确认 = 拦得住），本次 E2E 的交互提问三选一即「拦得住」的真实用例。文档写作方法（每问配「你能看到什么 / 具体是什么 / 为什么重要」三列表格）值得产品文档借鉴。

## 多项目的看板区分与切换（2026-11-21 用户追问）

**问题**：工作台把每个项目的看板纵向平铺，块与块之间只有留白、没有容器边界；项目数增长（5 个以上）会变成一条无区分的长滚动页。

**设计决策**：改为「项目切换条 + 单看板视图 + 看板容器化」——
- 看板区顶部新增项目切换条：每个项目一枚 chip（状态点 + 状态文字 + 目标截断），选中项高亮（`border-selected` + 填充）；同一时刻只渲染选中项目的看板与资产，页面长度不随项目数增长。
- 摘要条、右侧配置栏、资产表全部跟随选中项目（`primary` 从「固定取最新项目」改为「取选中项目，缺省回落到最新」）。
- 看板区块容器化（边框 + 卡片填充 + 内边距），与摘要条、资产表、计划卡的既有容器语言一致。
- 单项目时不显示切换条（无信息量）；全屏看板不受影响；A2 的看板/列表视图状态按项目记忆，切换回来保持原视图。

**验证**：预览库 4 个项目（已完成 hello / 执行失败 hello / 正在返工 看板 UI / 已完成 Gomoku）切换自如，右栏「计划版本 2」「资产 3」跟随选中项（截图 `58-项目切换条默认.jpeg`、`59-项目切换条切换后.jpeg`）。

**遗留观察**：多次执行/重试会各生成一个项目条目，同目标的条目靠状态文字区分；「执行历史合并展示（如已完成项折叠为一枚 chip）」是数据模型层面的产品问题，留待后续评估。

## 遗留

- Marvis《隐私与数据安全》（L2 硬垂询细节）与《核心功能与使用场景》两页值得后续补充阅读。
- 花名册员工的职责语义（注入任务）与 Marvis 的角色定位命名同源，但「角色化命名让用户无需理解调度逻辑」这一点可反哺员工编辑器的文案（说明域已为此铺路）。

## 执行状态机遗留：中断检测与自动迁移（2026-11-21）

**现象**：服务重启时，运行中（running / reviewing 等在途状态）的检查点没有终态迁移——看板该任务永久停留在「进行中」，续跑被执行准入的 CAS 拒绝（准入只接受 released / awaiting-direction / blocked 三类状态）。

**当前恢复路径**（E2E 已两次验证可行）：向主助手提出调整 → 保存修订计划（新版本）→ 工作台确认 → 按新版本重执行。人工干预可走通，但每次服务重启后需要用户手动触发一轮。

**后续深改方向**：执行状态机在启动时扫描在途检查点并自动迁移为可判定的终态（如 interrupted），使续跑准入直接放行。这涉及执行状态机与准入逻辑的核心改动，不属于界面层修复，单独立项处理；在那之前，看板对「重启后永久进行中」的任务展示保持现状，恢复依赖上述人工路径。

**修复版补充（2026-11-21 晚）**：针对「执行中无法停止、只能卡住」的反馈，工作台在途任务摘要条新增「停止执行」按钮（`project.stop`），调用 `projectDashboard.stopExecution(sessionId)` → `agent.cancel({ kind: 'user' }, { keepInbox: true })`：在途 `project_execute` 被中止并写入 `interrupted` 检查点，排队中的用户输入保留。用户随后可走既有「提出调整 → 修订计划 → 确认 → 重执行」链路。该按钮解决「运行中」的卡住；由服务重启导致的「僵尸 running 检查点」仍需上述启动迁移深改，不在本批范围。
