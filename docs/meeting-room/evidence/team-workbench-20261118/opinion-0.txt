## 二、从文件中确认的事实（决定方案的关键点）

1. **v020 冻结源共 22 个文件，manifest 为 21 个源文件登记 `source_hashes`**；主控制节点为 `00_normalize_alert`、`01_initialize`、`02_prepare`、`03_accept`、`04_merge`（另有 loop 版本）。所有节点以 `handler(params)` 收参，`initialize` 的 state 明确不含 `memory_context`（[01_initialize.v020.py](scenarios/ndr/snapshots/research-ndr-v3/coze_nodes/versions/v020/01_initialize.v020.py#L70-L77)）。
2. **记忆接入点是 `prepare` 之后、模型调用之前**：`prepare()` 返回 `model_user_input` 字符串（[runtime.v020.py](scenarios/ndr/snapshots/research-ndr-v3/coze_nodes/versions/v020/runtime.v020.py#L262-L263)），本身没有记忆字段。因此接入必须是“冻结节点之外的包装/接线”，不能改 v020 源。
3. **裁剪 CLI 契约**（[compact_investigation_context.py](packages/triage-memory/scripts/compact_investigation_context.py#L12-L100)）：
   - 根字段必须含 `tenant/scenario/scenario_version/case_id/as_of/instructions/constraints/unresolved/budget_chars/optional_excerpt_chars/evidence`；
   - `evidence[*]` 必含 `id/source/observed_at/text/required`，且 `tenant/scenario/case_id` 必须等于根；`required=true` 原文完整保留，`optional` 按 `optional_excerpt_chars` 截断或置空；
   - `memory_context` 若出现，必须有 `tenant/scenario/scenario_version/source`，前三者必须等于根，历史 `case_id` 可不同；CLI **原样拷贝整个对象**进 `memory_reference.context`；
   - 退出码：`0` 成功、`2` `budget_exceeded`（写入文件但下游必须阻断）、`1` 输入/写入错误（不保证无残留、不得覆盖已存在输出，`open('x')`）；`output_chars` 是确定性字符数，不是模型 token 预算；**不是原子写**，调用方必须等 exit 0 再解析 JSON。
4. **发现两处契约不一致（本阶段只记录，不修）**：
   - `memory-context.schema.json` 要求 `policy` 常量为 `reference_only_no_label_copy`，而代码 `POLICY_VERSION` 为 `reference_only_no_label_copy/v1`（[constants.py](packages/triage-memory/triage_memory/constants.py#L3-L6)）；
   - `memory-context.schema.json` 是 `additionalProperties:false` 且不含 `tenant/scenario/scenario_version/source`；而裁剪 CLI 要求并原样保留这些 scope 字段，`investigation-context.schema.json` 的 `memory_reference.context` 又只允许这 4 个字段 + `additionalProperties:false`。**即：把完整检索上下文（含 `policy/counts/similar_cases`）传给裁剪 CLI，输出必然不满足 investigation-context schema**。必须由需求明确“传给裁剪的 memory_context 是 envelope-only，还是完整检索上下文”。
   - 另外，CLI 代码并未 import/读取 schema 文件，“按 schema 校验”是文档表述，验收时需明确以 CLI 实际校验规则为准，避免误判。
5. **测试基线**：[test_investigation_context.py](packages/triage-memory/tests/test_investigation_context.py) 共 5 个测试方法（确定性/必需保留、超预算与省略、9 类 scope 拒绝、预算边界与文件保护、非法输入），覆盖 scenario=`rasp` 的模块行为，**不覆盖 NDR/web 接入**，也不校验输出是否符合 schema。
6. **历史实验的定位**：DR-020 明确“冻结 v020 与 current 保持原样，使用来源 SHA 校验的独立副本验证；n8n 是本地等价模拟，不是生产编排”。背景实验证明了 WSL n8n 2.47.7 + 隔离 `N8N_USER_FOLDER` + `import:workflow`/`execute --id` 的可行性，但其模型调用依赖 bridge/DSH 路由；本次要求不依赖模型适配器/bridge，因此是**新的、更小的流程**，旧证据不可复用。

## 四、接入方案建议（写进研发说明的骨架）

**数据流（不修改任何冻结节点）**：

```
v020 输入(合成) → 01 initialize → 02 prepare（产出 model_user_input）
                                      ↓
                       接线层：组装裁剪输入
                       { tenant, scenario, scenario_version, case_id, as_of,
                         instructions, constraints, unresolved, budget_chars,
                         optional_excerpt_chars,
                         evidence:[{id:"model-input", source:"v020 prepare",
                                    observed_at, required:true, text:model_user_input,
                                    tenant,scenario,case_id}],
                         memory_context: <envelope> }
                                      ↓
               compact_investigation_context.py --input / --output
                                      ↓
                  exit 0 + JSON 解析成功 → 方可继续
                  exit 2 / exit 1 / 解析失败 → 立即阻断（DR-020 失败语义）
                                      ↓
        模型可见上下文 = 压缩输出 evidence[0].text（必需证据原文不变）
                       + 独立的“历史相似案例参考”提示块（来自记忆检索结果，非证据）
        压缩输出中的 memory_reference.role = historical_reference_not_current_evidence
```

**记忆形态建议（需用户确认，见待定点 4）**：
- 传给裁剪 CLI 的 `memory_context` 采用 **envelope-only**：`{tenant, scenario, scenario_version, source}`（可加历史 `case_id`），这样输出满足 `investigation-context.schema.json`；
- 完整检索对象（`policy/counts/similar_cases`，即 [context.py](packages/triage-memory/triage_memory/context.py#L17-L57) 的产物）只用于生成“历史参考”提示块，不进入 `evidence`，也不进 `key_Evidence`；
- 在研发说明中明确记录“完整检索对象直接传给 CLI 会导致 `memory_reference.context` 多字段、违反 output schema”，作为已知缺口和本次验收的边界说明。

**失败语义（必须写死）**：exit 2 与 exit 1 均不得进入后续模型/后续节点；不得用“文件已出现”判断成功；输出文件不得覆盖已有文件；每次运行用唯一输出名。

| n8n 进程内部 IPC/命名管道在受限沙箱下失败 | `execute` 起不来 | P0 试跑一次最小导入/执行；失败即记录为环境阻塞 |
| n8n `execute` exit 0 但业务失败 | 误判通过 | 强制业务断言（exit code/JSON/role/sha256），禁止只看 n8n 状态 |
| 裁剪 CLI 非原子写/不覆盖 | 读到半成品或被 `x` 模式拒绝 | 唯一输出名 + 等 exit 0 + 解析校验；覆盖写单独作为保护性测试 |
| `memory-context` 契约不一致（policy 常量、scope 字段与 `additionalProperties:false`） | 若按完整检索对象验收会“必然失败”或误判 | 计划明确 memory_context 形态（建议 envelope-only）；把完整对象→schema 的差异记录为已知缺口，不修改 schema/代码 |
| NDR 语义被模块测试掩盖（测试用 `scenario=rasp`，CLI/测试不校验 output schema） | 误以为 NDR 已验 | 额外要求 NDR `scenario=web` 合成 fixture 的 CLI 实跑 + 独立的只读 schema 子集校验证据 |
| 旧实验证据被当成本次执行 | 交付不真实 | run_id 前缀 `team-workbench-20261118-`、全新时间戳/临时目录、验收 B8 逐项比对；旧目录只允许作为背景引用 |
| 输出目录漂移 | 违反硬边界 | 交付只写 `deployments/team-workbench-20261118/`；验收用 `git status --porcelain` 前后快照证据确认 |
