# 迭代计划与评审

本页按"角色讨论 → 结论 → 迭代排期 → 文档与评审规则"组织。今天的讨论由我代四个角色推演（当前环境没有 API key，未真实运行多 Agent），结论可复核；接入模型后可用 `meeting_start` 重跑同一议题做对照。

## 角色讨论（推演）

**产品**：用户要的是"说一句话，拿到可验收的交付"。因此每个迭代必须有可演示的切片，不能只交底层能力。优先级：主助手入口与会议可见性 > 任务与验收 > 技能/MCP > 迁移。

**架构**：会议 = 根会话 + spawn 子代理这条已经验证；接下来最大的风险不是隔离，而是**可观测**与**编排落库**。每迭代只引入一个新机制，避免同时改会话模型和存储。

**测试**：当前最大欠账是审批配对与桌面加载。桌面受网络阻塞，先记为阻塞项而不是降级跳过；审批配对必须在 I1 内补上，否则后续所有"关键动作需审批"都缺证据。

**交付**：两天的迭代必须留半天做记录与推送，否则进度不可信。文档只保留"决策 + 判据 + 结果"，不写过程流水账。

## 迭代节奏

- **周期**：2 天/迭代，第一天做实现，第二天上午测试、下午记录与推送。
- **完成定义**：代码合并 + 该迭代门禁通过 + `06-实施记录` 有对应条目 + 已推 Gitea。
- **强制项**：每迭代至少一条自动化测试；每个新公开行为有 README 说明；不通过不推送。
- **可选延后项**：任何依赖外部网络或签名的工作，标注阻塞原因后可顺延，但不得静默跳过。

## 迭代排期

| 迭代 | 必做 | 可选/顺延 |
|---|---|---|
| I0（已完成） | 规划与纪律、首轮隔离、插件包、工具与审批前置 | 桌面验证 |
| I1 | 审批配对测试（`approval/asked`↔`decided`）；会议落库投影（发言引用会话事件）；Gitea 推送与工单建立 | 桌面加载 |
| I2 | 会议列表/详情两页（假数据）；侧栏入口；locale 字典 | 真实会议数据接入 |
| I3 | 讨论轮与争议台账（`round`/`objection`/`decision`）；状态机迁移校验 | 并行轮次 |
| I4 | 任务与验收（产物指纹、返工、预算拦截）；业务审批页面 | 技能路由 |
| I5 | 技能/MCP 管理页；迁移导入；安装包 | 云端能力 |

## 文档设计

| 文档 | 职责 | 更新时机 |
|---|---|---|
| `01` 目标与定位 | 不变的为什么 | 目标变化时 |
| `02` 产品设计与交互 | 页面与交互契约 | 页面变更前 |
| `03` 技术方案与阶段计划 | 架构、数据模型、阶段判据 | 机制变更前 |
| `04` 执行目标与发布纪律 | 节点、推送规则 | 节奏变化时 |
| `05` 测试计划 | 分层与每迭代用例 | 新判据出现时 |
| `06` 实施记录 | 逐条事实：计划/问题/测试/结论 | 每个迭代结束 |
| `07` 本页 | 排期与评审规则 | 每迭代开始 |

规则：一页一个职责，事实只写在 `06`，结论变更另起一条，不回头改写历史。

## 评审规则

1. **自检**：门禁命令 + 本迭代新增测试的实际输出，写进 `06`。
2. **对照契约**：新增行为是否在 README 或 `03` 中有对应描述，没有则先补文档。
3. **可观测性**：新能力若无法被用户或测试观察到，不算完成。
4. **回退**：每个迭代结束确认能回到上一迭代状态（提交点 + 数据兼容说明）。
5. **推送**：迭代结束推 Gitea；每个 sprint 版本推 GitHub `meeting-room` 分支；工单不受此限。

## UI 设计协作（I2）

设计师介入点是会议列表页与会议详情页。交付物：两页高保真，桌面基准宽度 1440，含列表项/阶段条/成员/争议台账/产物区；空态、加载态、错误态可后补。风格基准取当前 DSH 会话页截图（侧栏、状态色、头像、折叠长文本）。评审时对照 `02` 的信息架构逐项确认，缺失项写回 `02`。
