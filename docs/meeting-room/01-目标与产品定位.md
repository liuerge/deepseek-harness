# 目标与产品定位

## 工程整合范围

本产品以 DSH 为底座，通过自有 Host 插件、Client 页面和 bundle 整合主助手、可复用数字员工与团队、逐员工模型和技能/MCP 配置、会议协商、史官记录及项目交付。用户通过主助手下发需求，通过工位、任务与成果查看真实执行，按授权控制验收、纠偏和工作时段。原会议室业务规则和数据按盘点结果迁入。工程对应关系与任务见[开发任务拆解与里程碑](12-开发任务拆解与里程碑.md)。

## 当前产品目标（2026-11-17）

用户提交多个需求，主助手组织数字员工完成需求澄清、产品定义、方案验证、开发实施、验收交付。员工使用已配置工具，保留可检索的执行与交接记录，用户可以观察实际产物并随时修正方向。会议用于需要协商的流程节点。

产品验收覆盖真实工具调用、需求版本与决策记录、任务依赖、成果验收、项目暂停恢复、多项目容量和工作时段。7×24 运行需要常驻 Host、预算及重启恢复策略。以下参考产品与历史范围供设计参考，实施顺序以当前迭代计划为准。

## 多厂商数字员工

每名员工独立选择模型连接（provider）和模型，同一团队的主助手、执行员工、会议角色和验收员工可以使用不同厂商。主会话的全局模型选择不能替代员工配置。既支持统一网关提供的多种模型，也支持多个厂商的独立 API 与兼容服务；复用 DSH 的模型接入和凭据管理，员工及确认计划只保存配置引用，不保存明文密钥。所选连接不可用时明确失败，不静默改用主助手模型。

验收至少覆盖连接 A 实际调用工具交付、连接 B 独立检查、不同连接员工参与会议，以及会话日志中的实际模型路由。单一 OpenCodeGo 连接的真实测试不代表多厂商接入完成；合成适配器回归不替代真实厂商联调。近期配置与联调任务见[近期实施顺序](12-开发任务拆解与里程碑.md#近期实施顺序)。

## 一句话目标

把"会议室"从讨论工具升级为**可验收的数字员工团队**：用户只提供方向，主助手负责拆解、开会、调度、交付，用户只做关键决策和最终验收。

## 流程参考

阶段划分参考 GOV.UK 的需求研究、方案验证、实际建设和持续运营，任务完成与成果检查参考 Scrum 的产品目标、待办列表和完成定义。项目采用的具体角色、产物及验收条件见技术方案。[GOV.UK 交付流程](https://www.gov.uk/service-manual/agile-delivery) · [Scrum Guide](https://scrumguides.org/scrum-guide.html)

## 用户痛点（来自现有产品使用）

- 现有底座在工具、技能、桌面体验上偏弱：Agent 能讨论，但"像真实员工一样找文件、执行工具、用技能"的能力不够。
- 多 Agent 会议有价值，但过程不够透明：谁在做什么、中间结果是什么、最终产出在哪里，需要更直观。
- 用户不想自己配置工作流/技能；希望开箱即用，同时保留深度定制空间。

## 产品定位

**一个本地优先、桌面可用的多 Agent 工作台**：
- 主助手（SuperAgent）是唯一对接人：理解目标、拆解任务、调度角色 Agent、汇总交付。
- 会议用于协商与评审：角色 Agent 按治理流程讨论（独立首轮、争议裁决、独立终审），产出方案。
- 任务与验收闭环：执行、审核、验收、返工、产物登记、预算与调用上限。
- 能力可扩展：技能（SKILL.md）、MCP/CLI、自定义 Agent；能力 Agent（文件/搜索/浏览器/系统）给角色 Agent 使用。
- 过程透明 + 关键动作审批：看得见、拦得住。
- 桌面应用（Windows），本地数据、本地模型/网关，不依赖云。

## 参考产品与取舍

### Marvis（腾讯）的设计点
- 一个主 Agent 总指挥：一句话 → 拆解 → 调度 → 汇总，用户不配置工作流。
- 出厂预置能力 Agent：File / Computer / App / Browser / Search，开箱即用。
- 过程透明：当前步骤、哪个 Agent、中间结果、最终产出；日志可追溯。
- L2 硬审批：关键动作必须用户确认。
- 可扩展但不强制：自定义 MCP/CLI、导入 Skill、自定义 API。
- **借鉴产品原则，不复制其 UI 资产或文案。**

### DSH 的能力（底座）
- 插件化（Cordis），Web + Electron 桌面，会话/Agent 循环、工具、MCP、技能、模型适配器。
- 适合承载"主助手 + 会话 + 工具执行"；多 Agent 会议的编排需要我们在插件里实现。
- 开发者预览期：固定版本、加适配层，不追每个上游提交。

### 现有会议室（业务规则来源）
- 已有：项目/员工/团队、讨论治理（独立首轮、异议台账、独立终审）、任务生命周期、验收、预算、主助手、员工/团队评价、技能 v1/v2。
- 这些业务规则保留，作为新产品的领域逻辑；UI 与运行时迁到 DSH。

## 核心差异化（不要丢）

1. 会议治理：不是"多 Agent 随便聊"，而是有独立首轮、争议逐项裁决、不同作者终审、发布门槛。
2. 任务与验收：真实产物和检查证据，验收团队按确认标准检查，各节点按授权自动放行或由用户复核。
3. 角色与能力分离：角色 Agent（产品/架构/开发/测试/验收/运维/数据）负责决策与交付；能力 Agent（文件/搜索/浏览器/系统）作为工具。
4. 主助手统一入口：用户只和主助手对话；会议与任务都是它调度的协作单元。
5. 本地优先与审计：数据、日志、审批都在本机。

## 非目标（本阶段）

- 不做云端多租户、团队协作服务器。
- 不开放无审批的原生系统工具。
- 不复制 Marvis/DSH 的源码 UI 资产；只借鉴信息架构与交互原则。
- 不追求一次迁移全部历史数据；先新库、后导入。

## 主会话统一指挥

实施优先复用并打通 DSH 已有的主会话、子智能体目录、共享任务板与工具记录。用户通过主助手组织团队，主动查看实际进度和成果，在主会话提出纠偏，会议按需辅助。新增业务能力围绕现有执行入口接入；任务状态整合先于扩展新的工位或看板页面。职责及整合顺序见[技术方案](03-技术方案与阶段计划.md#既有能力复用与状态归属)和[近期实施顺序](12-开发任务拆解与里程碑.md#近期实施顺序)。

用户日常只向主会话提出需求与纠偏，主助手负责更新计划、传达变更和协调执行。子智能体会话是观察与追溯入口，直接跟进或停止子会话保留为高级操作，不作为正常项目流程的前提。会议是主助手按需使用的澄清、协商和评审手段，角色意见、主助手结论与已确认需求分别留存。

复用现有会话页头的子智能体目录、执行会话和扩展位置。项目工作台负责整体目标、任务与交付；会话更多菜单负责发起会议和查看本会话记录。项目任务摘要读取既有检查点，不把已产出等同于验收通过，也不创建一套重复的员工聊天记录。

## 执行理念与暂停约定

参考独立 SuperAgent 原型的接单、派工和恢复机制，以及 Lauren Tan 的 pstack 工作方法，复用 DSH 主会话并按任务选择执行流程。简单需求可以直接实施与验收，会议和阶段检查按复杂度、风险及已确认标准采用。参考范围与补充场景见[对照资料](13-SuperAgent与pstack对照及补充场景.md)。

用户已确认暂停语义以 SuperAgent 原型为准：暂停自动调度及输入递送，正在运行的员工回合继续，不强制中断或等待全部收尾后才确认调度暂停。界面分别显示调度是否暂停和仍在执行的员工；完整规则见[治理基线](11-项目治理与验收基线.md#暂停与恢复语义)。
