# 数字员工模型路由加固：改动决策与复核依据

本页记录提交 `c691a9ee69`（**数字员工：补齐模型路由授权、推理档位与备用链**）的逐项决策：改了什么、参考了什么、为什么改、期望达到什么效果。目的是让后续复核能沿「结论 → 证据 → 代码」的链路回溯，而不必重读一轮调研。

上游依据见 [外部插件与官方能力调研](26-外部插件与官方能力调研.md)；那一页回答「生态里有什么」，本页回答「我们据此改了什么、没改什么」。

## 一句话结论

三处问题同源——员工派发走 `ctx.subagents.startActivation({ agentOptions })` 直连，绕开了 `tool-subagent` 工具参数路径上的**授权校验**与**档位继承规则**。本次不再分头打补丁，而是抽出一个 `employee-route.ts` 统一收口，并把两个新字段（档位、备用链）贯通到保存、校验、派发、UI 四层。

## 决策矩阵

| 决策 | 参考来源 | 出处性质 | 采纳/不采纳 | 判断理由 |
|---|---|---|---|---|
| 自建授权校验，不改官方文件 | 调研 §二：`assertAllowedModelSelection` 只在 `tool-subagent` 工具参数路径调用；用户直连路径不经过 | 源码事实 `packages/subagent/tool-subagent/src/model-selection.ts:146`、`:164` | **采纳** | 加白名单能堵住"员工可跑在用户从未授权路由上"的漏洞；改官方包会破坏 upstream 滚动升级 |
| Host `enabled=false` 时按不限制放行 | 同上：`allowedRoutes()` 在 disabled 时返回 `undefined` 且不读不校验 | 源码事实 `model-selection-settings.ts:47-56` | **采纳** | 宿主默认 `enabled=false`（`:32`），若照搬"白名单空即拒绝"会让当前所有环境不可用 |
| 不接管宿主的 `INVALID_MODEL_SELECTION_SETTINGS` | 同上：enabled 但名单为空时宿主抛错 | 源码事实 `model-selection-settings.ts:53` | **采纳** | 那是宿主配置错误，应由宿主暴露；用户侧读不到就当无策略，避免把宿主故障变成项目失败 |
| 推理档位显式随员工档案走 | 调研 §二：`resolveChildAgentOptions` 在路由变更时 `delete resolved.reasoningEffort` | 源码事实 `packages/subagent/subagent/src/child-agent.ts:117` | **采纳** | 不改则"改员工模型 → 档位静默掉回默认"，用户无任何提示；用 `AgentOptions.reasoningEffort` 官方原生字段，零依赖 |
| 档位候选来自模型自身声明，不硬编码三档 | 调研：`resolveModelInfo().reasoning.efforts[]`；`dsh-agents` 的 LOW/MEDIUM/HIGH 硬编码被明确列为"不建议借鉴" | 源码事实 `packages/llm/llm/src/types.ts:413-432` + 调研结论 | **采纳** | 硬编码会把用户绑死在特定 provider；模型无 reasoning 元数据时不显示下拉，保持默认 |
| 备用链按角色/员工有序配置 | `dsh-plugin-subagent-director` 四级回退；`dsh-swarm-orchestrator` per-role ordered fallback chain；`dsh-agent-board` 力度路由 + 备用模型链 | 插件 README 确证（调研 §一） | **借机制采纳** | 用户已有 Employee 实体，比插件的 glob 规则更直接；不装插件，避免自带 store 形成双真相源 |
| 返工时按 attempt 切备用路由 | 调研 §三：`attempts as first-class history`（`@ready22race/dsh-team-task`）；OpenHands 源码查证其 Task 模型**没有** attempt 字段 | 插件 README + 源码双向确证 | **采纳（结合用户已有 attempt 计数）** | 用户已有 `rework.maxAttempts` 预授权，正是 OpenHands 缺的封顶语义；保留自己的计数，只借"每次尝试独立路由" |
| 档位不匹配时剥离并记录，而非静默降级 | `dsh-swarm-orchestrator` README：声明不含该档位的模型剥离 pin，不兼容时先在同一模型降档再轮换模型，不消耗 retry 预算 | 插件 README 确证 | **部分采纳** | 采纳"不静默"原则；本次只做到**显式传值**，未做完整 effort ladder，见下文「未做」 |
| 不检查员工 provider 是否注册 | 调研 §四：员工 `provider` 是 subagent provider（spawn/fork），不是 LLM provider | 源码事实 + 测试反证 | **修正采纳** | 初版用 `ctx.llm.listProviders()` 判断导致 mock provider 测试全挂；可用性交 `startActivation` 判定，它已抛 `UNSUPPORTED_CAPABILITY` 并由 checkpoint 记录 |
| 授权失败不做 fallback | 调研 §二：`assertAllowedModelSelection` 语义为硬拒绝 `MODEL_ROUTE_NOT_ALLOWED` | 源码事实 `model-selection.ts:164` | **采纳** | 授权是策略判定，若允许 fallback 等于绕过白名单 |
| 空 `fallbacks` 不序列化 | 回归实测：`employeeSchema.default([])` 让员工 JSON 多出 `fallbacks:[]`，snapshot 失败 | 测试事实 | **采纳** | 保持既有数据格式与快照稳定；schema 改 `optional()`，保存时空数组省略 |
| 不引入任何外部插件依赖 | 调研 §五：候选插件多自带 store + 派发器 | 调研结论 | **采纳** | 避免与 `meetings.sqlite` + Employee/Team 双真相源；所有改动用官方 API 落地，upstream 升级风险归零 |

## 逐项改动、原因与预期效果

### 1. 新增 `src/employee-route.ts`（统一路由解析）

| 项 | 内容 |
|---|---|
| **改了什么** | 新增 `assertHostRoute` / `resolveEmployeeRoute` / `resolveEmployeeFallback` / `employeeReasoningEfforts` 四个导出；Host 策略通过 `ctx.subagentModelSelection` 的服务形状读取，不 import 任何 `tool-subagent` 内部源码路径 |
| **为什么** | 三处派发点原本各自拼 `agentOptions`，授权与档位没有统一入口；新增字段后若继续散落，极易漏一处 |
| **期望效果** | 任何员工路由在保存与派发时走同一套校验；Host 未启用时零行为变化；Host 启用后非法路由被拒绝而不是静默使用 |
| **复核要点** | `ctx.subagentModelSelection` 在 Cordis 上可能返回 unresolved proxy，实现里检查 `typeof candidate.allowedRoutes === 'function'` 才算有效策略——这是测试大面积失败的真实根因，改动时不要去掉 |

### 2. Employee 增加 `reasoningEffort` 与 `fallbacks`

| 项 | 内容 |
|---|---|
| **改了什么** | `types.ts` 的 `Employee` / `EmployeeSaveInput` 加两个可选字段；`roster.ts` 的 `employeeSchema` 加校验；`roster-management.ts` 与 `roster-tools.ts`（`employee_save` 模型工具）两条保存路径同步；空数组不落盘 |
| **为什么** | 没有档位字段 → 换模型时档位丢失且无提示；没有备用链 → 单个 provider 额度耗尽就整项目停摆（本轮实测 opencode-go 五个模型全不可用，同期 deepseek 直连正常，正是这个场景） |
| **期望效果** | 员工可配置"这个模型用 high 档"；主路由不可用时返工自动切到下一条候选，不必人工改员工再确认计划 |
| **复核要点** | `fallbacks` 可选、空数组省略——否则既有员工 JSON 与对话快照都会变 |

### 3. 三处派发点统一接入（`index.ts` / `project-tools.ts` / `acceptance.ts`）

| 项 | 内容 |
|---|---|
| **改了什么** | 三处 `agentOptions: { provider: employee.provider, model: employee.model }` 改为 `resolveEmployeeRoute(...)`；`project-tools.ts` 的返工分支按 `rework.attempt` 调 `resolveEmployeeFallback` |
| **为什么** | 派发是授权与档位真正生效的唯一位置；漏一处就会出现"有些任务受策略约束、有些不受" |
| **期望效果** | 会议角色派活、项目任务派工、独立审核三条链路行为一致 |
| **复核要点** | `acceptance.ts` 的审核人同样受授权校验——审核人换模型时档位也需显式传 |

### 4. 客户端档位下拉与备用链编辑（`RosterEditor.tsx` + 8 语种 `locales.ts`）

| 项 | 内容 |
|---|---|
| **改了什么** | 模型选择框下方按所选模型的 `efforts` 渲染档位下拉（无元数据则隐藏）；新增备用路由多行文本域（每行 `provider/model`），解析抽成 `parseFallbacks` 纯函数；`connections()` 用 `resolveModelInfo` 补齐档位信息；8 套语种各加一个 `roster.fallbacks` key |
| **为什么** | 字段存了但 UI 不可编辑等于没做；档位候选必须来自模型声明，不能硬编码 |
| **期望效果** | 用户在员工编辑器里就能看到"这个模型支持哪些档位"并配置，无需改配置文件 |
| **复核要点** | 换模型时 `reasoningEffort` 被清空（新模型可能不支持原档位）——这是刻意行为，避免跨模型沿用无效档位 |

### 5. 新增 9 个单元测试（`tests/employee-route.spec.ts`）

覆盖：显式档位透传、无档位时省略、主路由越权拒绝、白名单内放行、Host 未启用放行、Host 错误不转嫁、备用路由按 attempt 解析并保留档位、无备用时返回 undefined、备用路由越权拒绝。
