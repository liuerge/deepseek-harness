# 接入形态分析

问题：会议室这个产品，应该以什么形式接入 DSH？本页给出三种形态的取舍与推荐组合。

## 三种形态

**A. 只做插件**：会议室作为 DSH 的一个插件，用户装进现有 DSH 使用。实现最轻，但产品边界会被 DSH 主信息架构稀释：会议列表、任务验收、Agent 库都要挤进别人的侧栏，用户看到的仍是"一个 coding agent 多了几个页面"。

**B. Bundle 产品**：DSH 当底座，会议室作为一套自有 bundle 与桌面外壳发布。用户拿到的是"会议室"，不是"DSH 插件"。DSH 提供会话、子代理、工具、MCP、审批、凭据，产品提供导航、治理、验收与品牌。

**C. 独立应用 + SDK**：自有前端，通过 DSH SDK/CLI 驱动 Agent。控制力最强，但要自己重做会话展示、审批交互、工具过程呈现，等于把 DSH 已经验证的交互再写一遍。

## 取舍

| 维度 | A 插件 | B Bundle 产品 | C SDK |
|---|---|---|---|
| 上手成本 | 最低 | 中 | 高 |
| 产品独立感 | 弱 | 强 | 最强 |
| 复用 DSH 能力 | 全部 | 全部 | 需自行补 UI |
| 与上游同步 | 跟随版本 | 固定基线 | 完全自主 |
| 会议治理落地 | 受主产品信息架构限制 | 自由 | 自由 |

## 定案（2026-11-15）

形态 **B** 已确认：基于 DSH 做自己的产品，功能复用，需求另加；DSH 是 MIT，必要时可以改。

修改上游的优先顺序固定如下，只有前一层做不到时才进入下一层：

1. **插件**：业务逻辑、工具、页面、审批，全部落在自己的包里。
2. **组合**：需要不同的默认能力集（模型、提示词、工具白名单）时，用 bundle 的 `cordis.patch.yml` 覆盖，不改代码。
3. **补丁**：确实需要核心行为变化时，把改动收在独立提交里并写明理由、影响面与回滚方式，避免散落在业务提交中。
4. **Fork**：只有需要长期偏离 agent loop、会话格式或工具执行语义时才 fork；fork 后必须建立上游同步节奏，否则升级会失控。

所有改动只发生在自己的 fork 分支（GitHub `liuerge/deepseek-harness`、Gitea `dev/meeting-room-dsh`），不改上游仓库、不向其推分支。上游每次发版后做一次同步迭代：拉取上游、合并到 `meeting-room`、解决冲突、跑门禁与构建、把结果记进 `06`。同步节奏跟随上游发版，不追每个提交。

判断标准：改动是否能被上游接受。能接受就按补丁提交并跟进合并；不能接受再考虑长期维护成本，不要默认 fork。

## 结论

会议室是**产品**，不是"DSH 的一个功能"：用户只关心会议、任务、验收，不需要看到通用 coding agent 的全部入口。因此形态选 B，但内部仍由插件构成：

1. `meeting-room`（host）：会议服务、`meeting_start` 工具、审批前置、领域状态。
2. `ui-meeting-room`（client）：`sidebar.panellist` + `main` 两个槽位，会议列表与详情。
3. `meeting-room-bundle`：`cordis.patch.yml` 声明组合，桌面与 Web 共用同一份编排。
4. 桌面：先用官方 Desktop 的 profile 装 bundle；产品化阶段做自有 appId、图标与签名的安装包，内置固定版本 runtime。

数据分工沿用已确认的结论：发言与工具过程在会话日志里（本就由子会话产生），`subagent/catalog` 提供父子关系，插件库只存会议状态机、轮次索引、争议与裁决。

## 为什么不选 C

C 的代价不是写代码，而是重做交互：过程透明、审批卡片、工具结果折叠、会话恢复，这些 DSH 客户端已经打磨过。会议产品的差异化在治理与验收，不在重新发明对话界面。

## 什么时候才考虑改核心

只有需要改 agent loop、会话格式或工具执行语义时才考虑。当前的会议编排完全落在插件与组合层，不需要动 `packages/core`。

## 迭代路径

- I1–I2：仓库内 experimental 包 + Web profile 验证，先把会议与页面跑通。
- I3–I4：抽出 bundle，用桌面开发模式加载，验证组合与数据目录。
- I5：独立安装包（自有品牌、内置 runtime），旧会议室数据导入。

## 风险

- experimental 包不能出现在默认产品组合里（隔离门禁），bundle 需要单独的产品分组或独立发布。
- 桌面安装包涉及签名与自动更新，成本高于插件本身，应放到最后。
- 一旦 fork 核心，上游升级成本会持续存在，除非确有必要，否则不采用。
