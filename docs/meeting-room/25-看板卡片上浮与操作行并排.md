## 本轮实测发现

### 发现一：深色上浮已达成

`d74b2ba6e3` 把卡片底色从 `--dsw-alias-bg-layer-2` 换成 `--dsw-alias-bg-layer-3`，实测两套主题的相对亮度符合「卡片比列底浅」：

| 主题 | 卡片底色 | 列底色 | 合成后列底 | 相对亮度（0.2126R+0.7152G+0.0722B） | 结论 |
|---|---|---|---|---|---|
| 浅色 | `rgb(255, 255, 255)` | `rgba(0, 0, 0, 0.04)` | 约 `rgb(245, 245, 245)` | 255.0 > 245.0 | 卡片更亮，上浮成立 |
| 深色 | `rgb(53, 54, 56)` | `rgba(255, 255, 255, 0.08)` | `rgb(21, 21, 23)` 背板上的 `rgb(40, 40, 42)` | 53.9 > 40.1 | 卡片明显更亮，上浮成立 |

列底是半透明白（`rgba(255, 255, 255, 0.08)`）叠在不透明背板 `rgb(21, 21, 23)` 上，不能直接拿它的 rgb 分量与卡片比亮度，必须先合成。合成后深色下卡片比列底亮约 14 个亮度级，配合 `--dsw-elevation-panel` 阴影，卡片读起来是浮起的面而不是内嵌的洞。

浅色下卡片 `rgb(255, 255, 255)` 与列底 `rgb(245, 245, 245)` 的差只有 10 级，是本轮**刻意保持不变**的行为——上一轮只改深色方向的材质，浅色沿用 `--dsw-alias-bg-layer-3` 与上一轮一致的观感。

### 发现二：「两按钮并为一行」实际未生效

上一轮把 `.card > button` 改成 `.cardActions { display: flex; flex-wrap: wrap; gap: 8px; }`，容器确实是 flex 行，但 `flex-wrap: wrap` 在**列宽不足时依然换行**。实测两按钮（「查看执行会话」+「任务与验收条件」）在 `md` 尺寸下需要 246px，而四类场景里操作行的实际可用宽度是：

| 场景 | 列宽 | 操作行可用宽 | 两按钮所需 | 结果 |
|---|---|---|---|---|
| 1780 内嵌看板 | 191px | 145px | 246px | 换行成上下两行 |
| 1780 全屏看板 | 290px | 244px | 246px | 换行（**差 2px**） |
| 1180 内嵌看板 | 152px | 106px | 246px | 换行 |
| 1180 全屏看板 | 204px | 158px | 246px | 换行 |

根因是五列布局下每列只有 150–290px，中文长按钮名放不下，与 `flex-wrap` 的取值无关。

## 本轮修复

### 修复一：按钮改用小号尺寸

卡片操作按钮加 `size="sm"`（控制高 28px、字号 12px、左右内边距 10px），与卡片内密集控件的密度一致，也让两个按钮从 246px 降到 204px。

### 修复二：压缩按钮文案（8 语种同步）

两个按钮文案缩短，语义不变、8 套语种一起改，避免同一条文案在不同语言下长度差异悬殊：

| key | 原文案 | 新文案 |
|---|---|---|
| `project.open-worker` | 查看执行会话 / View execution conversation | 查看会话 / View session |
| `board.task-detail` | 任务与验收条件 / Task and acceptance | 验收条件 / Acceptance |

这两个 key 只用于卡片按钮（`board.task-detail` 不用于详情面板标题），改文案不影响详情面板与既有测试断言——测试通过 `zh['board.task-detail']` 引用，改值后断言自动跟随。

### 修复三：操作行不再换行

```css
/* The card actions stay on one row; the narrow board columns shrink the labels instead of stacking the buttons. */
.cardActions { display: flex; flex-wrap: nowrap; gap: 8px; }
.cardActions > button { flex: 0 1 auto; min-width: 0; overflow: hidden; text-overflow: ellipsis; white-space: nowrap; }
```

`nowrap` 保证两个按钮始终在同一行；极窄列下由按钮自身收缩并省略文案兜底，不再退化成上下堆叠。

### 修复后的宽度核对

| 场景 | 操作行可用宽 | `sm` + 新文案所需 | 结果 |
|---|---|---|---|
| 1780 内嵌 | 145px | 144px | 同一行 |
| 1780 全屏 | 244px | 144px | 同一行 |
| 1180 全屏 | 158px | 144px | 同一行 |
| 1180 内嵌 | 106px | 144px | 收缩省略，仍为同一行 |

## 关于受阻/返工数据的说明

本轮的受阻与返工数据不是跑真实对话得到的，而是**直接写入预览库 `meetings.sqlite`** 的 `project_records` 表得到的。原因是 `opencode-go` 通道余额已耗尽（`https://opencode.ai/zen/v1/chat/completions` 返回 `402 Insufficient balance`），无法再跑一次带负例的真实执行。

依据是看板的数据通路与模型无关：`projectDashboard.timeline()` 直接 `SELECT ... FROM project_records ORDER BY sequence`，不按 Session 过滤，也不经过任何模型调用；列归属由 `columnOf(state)` 按 `state` 字符串决定。因此写入 `acceptance-blocked` 与 `reworking` 两态的 checkpoint 记录，与执行服务写入的行在结构上一致，看板渲染路径完全相同。

需要说明的边界：本轮因此**未覆盖**真实执行链路产出的受阻/返工数据——真实执行下 checkpoint 的 `handoff` 文本、`report.criteria` 的证据路径、返工的 `sourceCheckpoint` 指向都会带上真实运行痕迹，与本轮写入的构造值不同。上一轮（round8）已在真实数据上验证过执行链路，这部分不重复。
