# 插件开发约束与交付指南

本文固化数字员工项目工作台插件的开发铁律、官方 API 边界、构建打包与交付方式。它描述的是工程约束，不是产品规划；产品范围见 01–03 号，回归用例见 34 号。

## 铁律：插件开发不许改 DSH 底座

产品线改动只落在三个插件包与 `docs/meeting-room/` 内。任何需要修改底座源码、底座构建脚本、底座 tsconfig 或底座测试才能编译通过的设计，都是错误设计，必须改为只依赖官方底座已公开的能力。这条约束优先于交付进度：宁可裁剪功能，也不改底座。

这里的底座指 `packages/` 下除三个插件包以外的所有包、`apps/`、`vendor/`、`scripts/`、根 `tsconfig*.json` 与根配置。插件指 `packages/experimental/meeting-room`（Host）、`packages/experimental/client-ui-meeting-room`（Web 客户端）、`packages/experimental/meeting-room-bundle`（组合包）以及本目录文档。唯一的例外是仓库把插件纳入文档/目录生成而必需的脚本条目与生成物（如 `scripts/gen-cordis-catalog.ts` 的豁免、`gen-doc-graphs.ts` 的角色、`packages.md` 目录、`api-catalog.ts` 生成物），这些不改变底座运行时行为，且必须由对应生成脚本产出而非手写。

### 违规案例与官方替代

本插件早期为图方便改过底座，导致拷到干净官方源码无法编译。下表是已撤销的改动与现在的官方替代，后续开发遇到同类需求按右列处理，不得回退到左列。

| 曾改的底座能力 | 违规做法 | 现在的官方替代 |
| --- | --- | --- |
| 打开模型设置页 | 新增 `settingsNavigation` 服务 | 在插件面板内用官方 factory `renderFactorySlot('settings.section.view', { id: 'models', close })` |
| 团队选择器挂载点 | 新增 `conversation.hero.agentPreset.suffix` / `.options` slot | 官方 `conversation.hero.options` 与 `conversation.input.model.options` slot |
| 实验包身份登记 | 在 `scripts/experimental-package-policy.ts` 例外名单加包名 | 包名使用官方 `@deepseek-ai/dsh-experimental-` 前缀，自动识别 |
| Typert 远程声明 | 在根 `tsconfig.host.json` 加插件引用 | 绝不改根配置；远程声明是构建期产物，不是运行时依赖 |

### 如何验证没有改底座

提交前用干净官方源码基线比对，输出必须为空（下例只看底座运行时源码，文档生成脚本与生成物除外）。

```sh
# <official-base> 指与本产品版本对应的官方 deepseek-harness 发布标签或干净检出
git diff --name-only <official-base> -- packages/ apps/ vendor/ | grep '/src/' | grep -v 'experimental/.*meeting-room'
```

更强的验证是把三个插件包单独复制到一份**干净的官方源码**上，只运行 `pnpm install` 与插件自身的 tsc/构建，不做任何底座补丁。当前版本已在官方 rc.5 源码 + WSL Ubuntu24 上通过：host/client 编译零错误、client bundle 构建成功、UI 与预置团队正常、浏览器零 JS 报错。

## 只依赖官方 API 的实现清单

客户端插件当前使用的公开能力全部来自官方底座，不引入任何自定义服务或 slot。

| 需求 | 官方能力 | 来源包 |
| --- | --- | --- |
| 侧栏入口与面板 | `main` slot | `dsh-client-ui-slots` |
| 模型设置内联视图 | `settings.section.view` factory | `dsh-client-ui-settings` |
| 对话头部团队入口 | `conversation.hero.options` slot | `dsh-client-ui-conversation` |
| 模型下拉团队项 | `conversation.input.model.options` slot | `dsh-client-ui-model-selection` |
| 会话头动作 | `conversation.session.header.actions` slot | `dsh-client-ui-conversation` |
| 外部应用打开文件 | 宿主 `openWorkspacePath` RPC | `dsh-api-session-controller` |
| 中止执行 | 底座 `agent.cancel` | 通过 Host 插件 Remote 暴露给客户端 |

TypeScript 侧用 `import type {} from '@deepseek-ai/dsh-client-ui-model-selection/client'` 引入 slot 类型，并在插件 `tsconfig.json` 加对应 project reference；这是插件自己的配置，不是底座改动。

## 包命名与版本

三个包统一使用官方实验包前缀，目录名不带 `experimental-`，与官方实验包惯例一致。

| 目录 | 包名 |
| --- | --- |
| `packages/experimental/meeting-room` | `@deepseek-ai/dsh-experimental-meeting-room` |
| `packages/experimental/client-ui-meeting-room` | `@deepseek-ai/dsh-experimental-client-ui-meeting-room` |
| `packages/experimental/meeting-room-bundle` | `@deepseek-ai/dsh-experimental-meeting-room-bundle` |

## 构建与打包

在仓库根目录对三个包分别做 TypeScript 构建，然后构建两个浏览器 bundle。

```sh
pnpm exec tsc -b packages/experimental/meeting-room/tsconfig.json
pnpm exec tsc -b packages/experimental/client-ui-meeting-room/tsconfig.json
pnpm exec tsdown --config-loader native --env.DSH_BUILD_FACE host --filter @deepseek-ai/dsh-experimental-meeting-room
(cd packages/experimental/client-ui-meeting-room && pnpm run bundle)
node .dsh-build/repack-meeting-room.mjs
```

`repack-meeting-room.mjs` 从构建产物装配四个 tgz：两个 `-fixed.tgz`、一个 `-bundle-fixed.tgz`、一个 `-client.tgz`。脚本会解析 workspace 依赖为具体版本，并把客户端版组合包的依赖改成指向本地两个 `-fixed.tgz` 的绝对 `file:` 路径，以绕开未发布的 registry 包。

### 桌面 exe 的 CSS 兼容

新版构建链把 CSS 作为 `meta().stylesheets` 交给宿主注入，靠宿主的 `DocumentStyles` 消费；rc.5 桌面 exe 的 web-frontend 早于该能力，内置插件仍是自己 `createElement('style')` 注入，不调用 `meta()`，因此只交出 CSS 的插件会功能正常但样式全无。这不是缓存或 CSP 问题。

打包脚本在 client-ui 的 `lib/client.js` 前置一段幂等的兼容 shim：提取 bundle 内的 CSS 纯文本，用旧宿主相同的 `style[data-plugin-css]` 去重键创建 style 标签。新宿主下这段 shim 与 `DocumentStyles` 的 `data-plugin`/`data-path` 标签共存，规则相同、不冲突。验证方式为 jsdom 执行 shim 得到 8 段 CSS 且重复执行不增标签，以及新版 web 下 8 + 222 个 style 标签共存、零 JS 错误。

## 安装与验证

客户端插件页安装只接受声明 `dsh.bundle` 的包，因此只能用客户端版组合包；命令行源码方式用两个 `-fixed.tgz`。完整命令、路径与重启要求见 `meeting-room-packages/README.md`。

预置团队在启动时尝试种入「软件开发专家团」，遍历所有模型 provider 选第一个能列出模型的；若全部失败则按设计留空，工作台显示补全配置提示，此时执行项目会在主会话给出 `PROJECT_ROSTER_EMPTY`，不静默按无员工执行。开发预览里看到的丰富演示数据来自独立种子脚本，不属于正式安装产物。

## 外部子智能体作为数字员工

Codex 与 Claude Code 子智能体插件通过 `ctx.subagents.registerProvider` 注册，属于**外部一次性执行引擎**，不是 `ctx.llm` 的模型路由。它们的 `capabilities.agentOptions` 为 false，模型与凭据由各自原生配置管理，启动时不能传 `agentOptions` 或 `agentPreset`。插件对它们的支持全部在插件包内实现，不改底座。

- Host `connections()` 会把已注册且 `agentOptions=false` 的 provider 合成为连接目录项（带 `external` 标记），因此「数字员工与团队」的连接下拉会出现 `codex` 与 `claude-code`；未安装对应子智能体插件时不出现。
- `saveEmployee` 对这些 provider 跳过 LLM provider 白名单与 Host 模型 allowlist 校验；派发时 `startActivation` 的顶层 `provider` 改为该引擎且不传模型/预设选项，其余员工仍走原来的 `agentOptions` 路径。
- UI 在选中外部引擎时显示提示：模型字段仅供参考，需先在插件页启用子智能体插件并完成其原生登录。凭据不经过 DSH 账户体系，父进程会清理凭据环境变量，需要密钥时在子智能体插件配置的 `env` 中显式提供。
- **主助手不能设为 codex/claude-code**：主助手由 `agentDefaultModel` 决定，只接受 `ctx.llm` 路由，而这些引擎是无状态、不继承父上下文的一次性子智能体，语义与实现都不适合常驻主会话。正确用法是让主助手通过官方 `subagent_codex` / `subagent_claude_code` 工具委派任务，或把这些引擎配置为项目执行中某一层数字员工的执行引擎。

验收证据：`external-subagent.spec.ts` 覆盖识别、路由、目录合成与缺省场景，RosterEditor 测试覆盖外部提示；WSL 预览实测下拉出现两个引擎、选中后保存员工成功、零 JS 错误，截图为 `06-codex-employee-options.png` 至 `09-codex-employee-saved.png`。

## 回归门禁

每次涉及插件改动，至少执行以下检查并把结论写入 34 号回归用例集。

```sh
pnpm run typecheck
pnpm exec vitest run packages/experimental/meeting-room/tests packages/experimental/client-ui-meeting-room/tests
pnpm run test:docs
```

当前基线为 typecheck 5 个 gate 全过、插件测试 209 个全过、文档门禁全过；干净官方底座 + WSL Ubuntu24 的构建与浏览器验证截图留在 `.screenshots/wsl-ubuntu24-ori/`。
