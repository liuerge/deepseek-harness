# SuperAgent 与 pstack 对照及补充场景

本参考对照当前数字员工工作台目标、本地 dsh-superagent 研究原型与 Lauren Tan 的 pstack，记录可借鉴能力、适用限制及新增验收场景。查阅日期为 2026-11-16。以下场景是设计建议，未自动转为已确认需求或已实现功能。

## 资料与核查范围

SuperAgent 来源为用户指定的本地目录 `C:\Users\nice\Documents\ChatGPT\harness研究\repos\dsh-superagent-prototype`，package.json 声明包名 dsh-superagent、版本 0.1.0、DSH 版本范围 ^0.2.1-alpha.2。已读取 README、理念、领域、执行说明及执行器、会话、持久效果队列和主 Session 工具源码；本次没有安装、运行或修改该原型。README 明确它是面向单个 GitHub 仓库的研究原型，并非正式产品，文章中的部分设计未实现。

pstack 来源为 [Cursor 官方仓库中的作者说明](https://github.com/cursor/plugins/blob/main/pstack/README.md)、[主工作流](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/SKILL.md)、[Orchestrate](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/orchestrate.md)及[决策记录](https://github.com/cursor/plugins/blob/main/pstack/skills/show-me-your-work/SKILL.md)。本次以这些原始文件为依据，未将转载文章的吞吐数字作为容量承诺，也未安装或执行 pstack 技能。资料中的工具、模型、云环境及发布权限属于其运行环境，需要按 DSH 能力和用户授权适配。

## 三者的关系

| 对象 | 已核对的职责 | 对当前工程的意义 |
|---|---|---|
| DSH 当前 fork | 主会话、子智能体、工具、Team、日志及插件扩展；自有实验插件增加计划和验收 | 继续作为运行底座与用户入口 |
| 独立 SuperAgent 原型 | 来源事件经过准入与研判，形成有授权范围的 Ticket，派给执行 Session，在来源渠道反馈 | 可借鉴接单去重、持久派工、执行槽位、输入递送与恢复；不等同于完整项目工作台 |
| pstack | 按任务选择工作方法，指定负责人及证据，独立核查真实成果，保存长期工作决定 | 改进主助手和员工执行规范，以及验收用例；不替代任务存储与调度器 |

SuperAgent 的 Main Session 已是主助手的同类实现。当前 fork 没有该独立包，不代表 DSH 缺少主会话委派能力，也不意味着应该再建一套聊天系统。此前把“DSH 底座”与“独立 SuperAgent bundle”放在同一能力条目中的写法不够精确，后续按上表区分。

## 与既有目标的对照

| 既有目标 | 原型或 pstack 的补充 | 需要保持的产品要求 |
|---|---|---|
| 用户只向主助手下达目标和纠偏 | SuperAgent 区分路由主会话与工作会话；pstack 协调者对成果负责 | 复用当前主会话，子会话用于观察；主助手传达并追踪新版本 |
| 标准产品开发流程 | pstack 按调查、缺陷、功能、性能及长期项目选择不同流程 | 阶段提供检查清单，按任务类型、风险与授权裁剪；简单任务不用走完整会议和阶段审批 |
| 员工真实调用工具 | 原型提供执行预设、目录准备及后台任务；pstack 要求检查实际应用或产物 | 能力不足必须显示，不能用报告文字替代真实检查 |
| 史官保存背景 | 原型保存工单、输入和派工；pstack 保存决定、理由、证据及结果 | 另需项目知识检索、替代关系与恢复前加载；持久工单不等于知识已被使用 |
| 预先确认验收和下游要求 | pstack 要求执行前明确完成证据，非作者检查当前版本 | 保留用户确认的自动或人工放行；验收报告不能自行扩大授权 |
| 多任务与持续运行 | 原型持久效果队列、并发槽位、工单目录及重启恢复 | 多项目隔离、预算、工作日历和未知外部结果核查仍须验证 |
| 下班暂停 | 原型暂停派发、研判与输入递送，运行中回合继续 | 用户已确认采用原型语义；分别显示调度暂停与员工执行，具体规则见治理基线 |
| 随时观察并提出建议 | 原型优先展示需要人处理的工作，pstack 保留可查决定 | 日常少打扰，同时保留用户主动查看完整轨迹、真实进度与成果的入口 |

原型的 Ticket 是授权工作单元，Assignment 是某次执行绑定，不直接替代当前 Project、Plan、Task、验收和员工身份。接入前需确定唯一状态归属，避免两套派工器各自启动相同任务。其执行器可无审批运行命令的部署假设不直接移入本产品；采用当前项目确认的工具权限和关键动作授权。

## 补充验收场景

下表的 P0 表示单项目闭环优先，P1 表示扩大并行前验证，P2 表示后续扩展。编号用于需求追踪，不表示已实现。

| 编号、优先级 | 用户场景 | 可检查的通过条件 | 对应原任务 |
|---|---|---|---|
| C01，P0 | 同一缺陷被重复提交，随后用户又补充说明 | 重复输入只产生一个授权工作单元；补充内容只递送一次并可追溯；不同独立目标可拆成不同任务 | T02、T05、T20 |
| C02，P0 | 修一个小缺陷，另一次只是查询代码行为 | 缺陷流程先复现再修复并验证；只读调查只交付有来源的结论，不强制开会或修改代码 | T01、T20、T22 |
| C03，P0 | Agent 宣称功能完成，但实际页面不能操作 | 验收通过真实入口执行关键路径，保存产物版本、操作及结果；无法运行时记无法验证，不能自动放行 | T06、T09、T10 |
| C04，P0 | 首次验收通过后，产物又被修改 | 旧结论只适用于旧版本；新版本重新检查受影响项，下游不消费未经放行的新产物 | T09–T11、T13 |
| C05，P0 | 我连续两次纠正相同错误 | 保存错误类别与原因，形成可运行的校验、类型约束或测试；再次违反时检查失败，仍保留来源和决定 | T11–T13 |
| C06，P0 | 任务遇到技术问题，但不需要我作业务选择 | 主助手按原因有限重试、缩小范围或重新分配；只将确实需要用户决定的问题提交，并列出证据、选项和受影响任务 | T05、T11、T13 |
| C07，P1 | 我提出多个需求，其中一个在等我答复 | 没有依赖的工作在预算与并发限制内继续；依赖该答复的任务等待；主会话纠偏可获得调度机会 | T05、T15、T16 |
| C08，P1 | 执行中重启 Host，之前可能已经创建外部成果 | 恢复读取当前目录、历史和外部结果；结果不明先核查，不重复提交或覆盖；未递送输入仍可追溯 | T05、T12、T14、T17 |
| C09，P1 | 我下班暂停自动处理，次日恢复 | 新派发、研判、超时处理、自动输入递送及对外回复暂停；运行中回合继续且状态可见，来源继续记录；恢复时重新核对授权与版本，保留待递送输入 | T12、T14、T17 |
| C10，P1 | 一个团队模板准备扩展到多组并行 | 先完成一项真实需求的执行、独立验收及交付；再增加隔离员工，验证写入范围、预算与集成冲突 | T15、T16、T18 |
| C11，P1 | 我离开数小时后查看进展 | 展示最近实际进展、产物、阻塞和需决定事项；决定可回查理由和原始证据；没有进展时不重复发送空泛汇报 | T07、T12、T17 |
| C12，P2 | 希望系统主动发现可修复问题 | 先按书面规则只记录候选，确认效果后再扩大授权；区分观察到的问题与允许修改的范围 | T01、T16、T17 |

## 实施建议与待确认项

近期实施顺序以[任务拆解](12-开发任务拆解与里程碑.md#近期实施顺序)为准，先接入已有 Team 任务和看板，再推进背景检索及纠偏。T05 的持久派工与恢复设计对照原型的 Ticket、Assignment、输入递送和 Effects；T14–T17 采用 C07–C10 验证暂停、隔离与持续运行。C01 随派工设计落实，C11 随真实进度与记录查询落实。C12 不作为当前默认行为。

直接安装整个 SuperAgent bundle 与复用其部分机制两种方式，需要先核对当前 DSH API、预设、工具权限、数据归属及是否同时存在两个调度所有者；本次不认定为即插即用。GitHub/飞书接单、自动合并、主动维护和云端员工不纳入默认范围。用户当前主会话入口、本地优先及已确认验收目标保持，暂停语义按本次用户确认采用 SuperAgent 原型。

完整目标、治理要求和任务状态分别见[目标与产品定位](01-目标与产品定位.md)、[项目治理与验收基线](11-项目治理与验收基线.md)和[开发任务拆解](12-开发任务拆解与里程碑.md)。本页只维护参考映射与补充用例。
